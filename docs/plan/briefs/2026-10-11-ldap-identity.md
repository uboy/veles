# Бриф: LDAP/AD группы (корпоративная идентичность, фаза AD)

- **Дата:** 2026-10-11. **Владелец:** Denis Mazur.
- **Эпик:** ldap-identity. **Ветка:** feature/ldap-identity, worktree `~/proj/veles-ldap`.

## Что делаем

Минимальный корпоративный вход: `POST /v1/auth/ldap {username, password}` ->
bind в каталоге -> группы пользователя (memberOf/posixGroup) -> маппинг в
группы veles -> выдача короткоживущего HS256-jwt (существующий контур).
Дальше все запросы идут с этим jwt - фильтр по группам уже работает до
evidence. Настройка env-ом, выключено по умолчанию.

## Почему так

- Блокер №1 продажи (оба ресёрча): первый вопрос ИБ - «как права из AD попадут
  в поиск». JWT уже поддержан (identity_mode=jwt на проде) - добавляется
  только источник личности.
- OIDC/Яндекс ID - следующая фаза того же эпика (после AD/LDAP): у RF-заказчиков
  первым спрашивают именно доменные группы.

## Границы

- Не делаем: SCIM/авто-провижининг, синхронизацию ACL из СЭД (P0-3), SSO-редиректы
  в вебе (каналы уже несут личность: WebUI act-as, токены).
- Тесты: in-process LDAP (ldaptor, в тестовой зависимости) - без внешних сервисов.

## Риски

- Инъекция DN (логин с спецсимволами) - экранирование обязательно, негативный тест.
- Пароли не должны попадать в логи - тест.
- ldaptor может не поддерживать часть черт - если упрёмся, минимальный RFC-совместимый
  заглушка-сервер на сокетах в тестах.
