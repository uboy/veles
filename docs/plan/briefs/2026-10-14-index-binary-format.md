# Execution brief: бинарный формат индекса (bm25 CSR + mmap)

Дата: 2026-10-14. Заказчик: Денис (го в ответ на разбор RAM фасада asrock 3.7 ГиБ).
Карточка: ai-tracker work/veles/task-veles-index-binary-format.md.
Ветка: feature/binary-index (worktree C:\Users\devl\proj\veles-bidx).

## Проблема

Фасад держит весь индекс в памяти как питоновские объекты. На прода-корпусе
asrock (233 775 узлов) куча процесса = 3.75 ГБ:

- bm25.json 113 МБ -> `Bm25Index.tfs: list[dict[str,int]]` = 233 тыс. словарей,
  суммарно ~1.2-1.6 ГБ RAM (главный пожиратель);
- meta.json 199 МБ -> node_meta (эту итерацию НЕ трогаем);
- numpy_matrix.npy 196 МБ -> резидентный ndarray;
- overlay.npz 781 МБ -> распакованный в память оверлей (лечится пересборкой
  базы, операционный шаг после ленда, не код).

## Что делаем (код)

1. Bm25Index v2: термины в CSR на чистом numpy (без scipy, её нет в
   зависимостях): indptr int64, indices int32, data float64; df - int64 array;
   term->row - dict; doc_lens - int64 array. Поиск векторизованный, формула
   Okapi BM25 ТА ЖЕ, арифметика float64, порядок суммирования вкладов для
   каждого дока - по порядку терминов запроса (как в текущем цикле), стабильный
   tie-break по индексу дока. Требование: бит-в-бит идентичность результатов
   search() со старой реализацией на одинаковых данных.
2. Формат: save пишет bm25.npz (savez_compressed: k1,b,avgdl, doc_lens, df,
   indptr, indices, data, terms, ids). load: если bm25.npz есть - читает его,
   если нет - старый bm25.json (обратная совместимость: стенды bm1/bm2
   поднимаются без пересборки). Старый save/load bm25.json не удалять из
   читателя.
3. add(): инкрементальное дописывание строк в CSR + df/avgdl пересчёт как
   сейчас. Инвариант K4 сохранить: ids дописывается последним, search в другом
   потоке безопасен (n_docs = len(ids), чтение по i < n_docs; для CSR -
   indptr/indices/data/doc_lens дописывать до ids).
4. mmap: в load_index базовая матрица np.load(mmap_mode='r') для
   NumpyFlatStore; add() материализует через vstack как сейчас (первый апсерт
   после старта возвращает матрицу в память - приемлемо); search @ работает на
   memmap. FaissFlatStore не трогать.
5. Оверлей (overlay.npz) и meta.json - без изменений формата.

## Что НЕ меняем

API, ранжирование/RRF, цитаты, канон, очередь загрузок, форматы meta.json /
numpy_matrix.npy / overlay.npz, поведение удаления.

## Критерии готовности

- Полный pytest зелёный (включая новые тесты: round-trip save/load npz,
  чтение старого bm25.json, бит-в-бит поиск CSR против эталонного цикла,
  add-во-время-чтения (K4), mmap-загрузка: поиск идентичен, add после mmap).
- eval: сквозная валидация - (а) эталонная реализация формулы в eval-скрипте,
  бит-в-бит на >= 300 запросах по синтетическому корпусу >= 2000 доков;
  (б) замер RSS процесса при загрузке большого bm25.json старым кодом против
  bm25.npz новым (ожидание >= 3x ниже); (в) время загрузки индекса старым
  против новым; (г) поиск по memmap-матрице == поиск по обычной.
- Ревью независимого агента: approved (high/medium нет).

## Риски

- Порядок сортировки при равных скорах - проверяется отдельным тестом.
- bm25.npz с dtype unicode - размер массива terms (проверить, что savez не
  разувает файл; при проблеме - terms отдельным json-списком).
- np.load(mmap_mode='r') на Windows (тесты локальные) и Linux (CI) - работает
  для .npy; файл матрицы не перезаписывать на живом mmap (save делает np.save
  в тот же путь только из CLI-пересборки, не из фасада - фасад матрицу не
  пишет, пишет очередь через append_overlay).
