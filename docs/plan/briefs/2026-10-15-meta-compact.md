# Execution brief: компактное RAM-представление меты индекса

Дата: 2026-10-15. Заказчик: Денис (го «заводи и делай» после поэтапного замера:
meta.json 413 МБ json = 2709 МБ RSS на прода-корпусе 235 754 узла).
Карточка: ai-tracker work/veles/task-veles-meta-compact.md.
Ветка: feature/meta-compact (worktree C:\Users\devl\proj\veles-meta).

## Проблема

После bm25-итерации (111cb90) мета - доминирующий пожиратель RAM фасада:
node_meta в питоновских dict'ах с полными текстами узлов = ~1.3 ГиБ из 2.15
GiB. Тексты - ~70% объёма меты и сжимаются zlib в 3-4 раза (русский корпус).

## Что делаем

1. Новый модуль veles/indexing/meta_compact.py: класс CompactNodeMeta -
   MutableMapping[str, dict], который ПОСЛЕ json.loads(meta.json) держит
   node_meta компактно:
   - тексты: один bytes-блоб (zlib level 1-2) + offsets int64 + длины int32 -
     ноль per-object overhead; распаковка ленивая при доступе m[nid]["text"];
   - интернирование повторяющихся строк: document_id, title, provenance
     (adapter, source_id), sha256_doc, revision_id, status - таблицы
     уникальных строк + int-индексы на узел;
   - access_groups: таблица групп + индексы (большинство узлов - одна группа);
   - редкие/нестандартные поля узла (asset, heading_path, lines, что угодно
     ещё) - в per-node compact-записи без интернирования;
   - материал: __getitem__ возвращает СВЕЖИЙ dict узла (полная dict-
     семантика для потребителя), get/items/values/len/contains - стандартные;
   - __setitem__: новые записи (узлы из очереди загрузок, K4) хранятся в
     отдельном plain-dict поверх и отдаются приоритетно; после setitem запись
     живёт как обычный dict (без сжатия) - их мало;
   - потокобезопасность как у текущего dict: загрузка строит структуры до
     публикации, чтение из другого потока безопасно, K4-инвариант цел.
2. Интеграция в indexer.py: load_index конвертирует meta["node_meta"] в
   CompactNodeMeta; bundle.save при записи meta.json собирает из компактной
   формы ПОЛНЫЙ payload (распаковка всех текстов - только путь CLI-пересборки);
   build_index и очередь пишут через node_meta[nid]=dict как раньше.
3. Все прочие потребители НЕ правятся: retriever (junk-фильтр :312/:330,
   evidence :351), app (:165 revisions, :179 titles, :202 evidence-обогащение,
   :919 снапшот), documents (:646, :741), image_index - работают через
   Mapping-интерфейс.
4. Формат ДИСКА и файлы (meta.json, bm25.npz, numpy_matrix.npy, overlay.npz)
   НЕ меняются. Пересборка индекса не нужна - только новый код.

## Что НЕ меняем

API, ранжирование, цитаты, канон, очередь, форматы файлов, скорость загрузки
(пик json.loads остаётся - отдельная работа).

## Критерии готовности

- Полный pytest зелёный (новые тесты: бит-в-бит доступа - все поля узла
  идентичны dict-версии на >= 5000 узлов синтетики; setitem+чтение из другого
  потока (K4); save после загрузки компактной формы == исходный payload
  (по-ключевое равенство с распаковкой текстов); image_index/retrieval работают
  на компактной мете; негативный: порча блоба даёт внятную ошибку, не мусор).
- eval: замер RSS на реальном прода-индексе bm1 (~/veles-rebuild/data, 235 754
  узла): мета компактно <= 0.5 ГиБ резидентно (против ~1.3-1.4 ГиБ dict-версии;
  на bm1 замерить обе), поиск по компактной мете возвращает те же evidence,
  что по dict-версии.
- Ревью независимого агента: approved (high/medium нет).

## Риски

- MutableMapping материализует dict узла на каждый доступ: hot-path
  (junk-фильтр по ~100-500 кандидатам) - измерить деградацию latency запроса
  (допустимо < 5%); при худшем раскладе - кэш последних материалованных.
- Потребители, мутирующие dict узла из меты (m["x"]=...), не должны молча
  терять правки: аудит потребителей на мутации (документировать в брифе
  исполнителя, при находке - решать через копию).
- K4: снапшоты list(node_meta.values()) в app/documents должны оставаться
  консистентными при добавлении из очереди.
