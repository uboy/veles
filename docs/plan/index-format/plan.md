# План: бинарный формат индекса (bm25 CSR + mmap матрицы)

Эпик: index-format. Дата: 2026-10-14. Бриф: docs/plan/briefs/2026-10-14-index-binary-format.md.
Заказ: снизить RAM фасада veles (3.7 ГиБ на asrock) без изменения результатов
поиска. Результаты поиска - бит-в-бит; стенды со старыми JSON-индексами
продолжают работать.

## Фаза 1: Bm25Index v2 (CSR на numpy) + формат bm25.npz

- Цель: tfs-словари заменены CSR (indptr int64, indices int32, data float64),
  df - массив, поиск векторизован, save пишет bm25.npz, load читает npz и
  старый bm25.json, add() инкрементальный, инвариант K4 цел.
- Файлы: veles/indexing/bm25.py, veles/indexing/indexer.py (только ветка
  загрузки bm25), tests/test_bm25_binary.py (новый).
- Критерий готовности: новые тесты зелёные - round-trip, чтение старого
  JSON, бит-в-бит против эталонного цикла (>= 300 запросов на корпусе
  >= 2000 доков), tie-break стабильный, K4 (add из другого потока).
- Чем проверено: python -m pytest -q tests/test_bm25_binary.py + существующие
  tests/ (все, что трогают bm25/search).

## Фаза 2: mmap базовой матрицы векторов

- Цель: load_index отдаёт NumpyFlatStore с матрицей np.load(mmap_mode='r');
  поиск и апсерт работают; faiss-ветка без изменений.
- Файлы: veles/indexing/indexer.py, veles/indexing/vector_store.py (только
  NumpyFlatStore при необходимости), tests/test_index_mmap.py (новый).
- Критерий готовности: тесты - поиск по memmap идентичен поиску по ndarray;
  add после mmap работает и save пишет полную матрицу; полный pytest зелёный.
- Чем проверено: python -m pytest -q (полный набор), CI Linux после ленда.

## Фаза 3: сквозная валидация + независимое ревью

- Цель: доказать эквивалентность и выигрыш на числах.
- Файлы: evals/index-format-validate.py, evals/results/2026-10-14-index-binary-format.md.
- Критерий готовности: eval-скрипт печатает VALIDATION-PASS: (а) бит-в-бит
  поиск CSR vs эталонный цикл; (б) RSS при загрузке: bm25.npz vs bm25.json
  (>= 3x ниже на синтетике 100K узлов); (в) время загрузки старый vs новый;
  (г) memmap-поиск == ndarray-поиск. Ревью: независимый агент, approved.
- Чем проверено: python evals/index-format-validate.py (код выхода 0), отчёт
  с числами, вердикт ревью в журнале карточки.

## Фаза 4 (операционная, вне кода): пересборка прода на bm1

- Цель: индекс asrock пересобран с вливанием оверлея (781 МБ -> пусто),
  перенесён на asrock, RAM фасада замерен до/после.
- Шаги: копия /data/canonical с asrock на bm1; сборка `python -m veles index
  --backend numpy` тем же EMBED_MODEL; контроль числа узлов до/после;
  перенос index-каталога на asrock (старый overlay.npz НЕ переносить);
  рестарт фасада; контрольные вопросы; docker stats до/после.
- Критерий готовности: healthz ok, число документов/узлов совпало, контрольные
  вопросы находят те же документы, RAM фасада <= 2 ГиБ.
- Чем проверено: вывод healthz/stats, журнал карточки.

## Расхождения плана и реальности

- Ф3 (б), ревью раунд 1: критерий «RSS при загрузке >= 3x» исполняется как
  ПРИРОСТ пикового RSS процесса при загрузке (сэмплы RSS в подпроцессе),
  а не как полный пик процесса: на 100к узлов полный пик даёт только 2.5x
  (527.6 vs 212.3 МБ), потому что одинаковая база интерпретатора+numpy
  (~100-130 МБ) размывает отношение; прирост загрузки 398.2 -> 85.9 МБ (4.6x,
  порог 3x сохранён). Первый вариант гейта на пик-аллокациях tracemalloc
  (6.7x) был подменой метрики - переведён в информационные.
  evals/results/2026-10-14-index-binary-format.md
- Ф1, ревью раунд 1: save() пишет bm25.npz И синхронный bm25.json (payload v1):
  после любой записи каталог читается старым кодом без пересборки - иначе откат
  на v1 был бы заперт окном пересборки (односторонняя дверь). Плата - transient
  tfs-словари на время сохранения (в живом индексе их нет) и второй файл на диске.

- Ф4: пересборка выполнена на bm1 за ~13 мин (планировали «дни на asrock»);
  RAM фасада 3.625 -> 2.151 GiB; выигрыш меньше исходной оценки «1.5-2 ГиБ
  только за счёт формата»: поэтапный замер bm1 показал доминирование меты
  (meta.json 413 МБ = 2709 МБ RSS) - она не входила в этот план.

- Ф6 части 2, прогон 1 (evals/results/2026-10-15-meta-compact.md): критерий (в)
  «latency < +5%» на индексе 2200 узлов давал +250-313% - на мелком индексе в
  отношении доминирует фиксированный оверхед ~150-250 полных материализаций
  меты на запрос (каждая с zlib-распаковкой текста, ~10 мкс), а не стоимость
  запроса. Починено в двух частях: горячий путь hybrid_search читает скаляры
  через CompactNodeMeta.get_fields без материализации, полный узел - один раз
  на запрос (memo; результаты бит-в-бит, полный набор 531 passed); гейт (в)
  замеряется на прода-масштабе 100к узлов (прод 235 754 по брифу), 2200 -
  информационно. После фикса на 100к: -2.9%/-2.7% и -1.6%/-4.1% в двух прогонах
  (шумовая эквивалентность; до фикса на 100к было +4.5%/+8.2%).
  evals/results/2026-10-15-meta-compact.md
- Ревью раунд 1 (medium): O(N)-обходы values()/items() при компактной мете
  материализуют каждый узел с распаковкой текста (50к: list(values()) 0.795 с
  против 0.001 с у dict) - гейт (в) мерил только hybrid_search, а секундную
  регрессию получали все мета-сканы (/toc-/stats, _resolve_revision,
  doc_titles, regroup, DELETE, supersede, tombstone, инвентарь картинок).
  Починено сканом выбранных полей CompactNodeMeta.iter_fields + диспетчером
  iter_node_fields (тот же dispatch, что get_fields): 8 мест переведены, на
  50к скан 1 поля 0.019 с (34x), 5 полей /toc 0.183 с (3.5x) - и без
  транзитного снапшота распакованных текстов (~1 ГиБ на проде);
  /v1/knowledge/stats и revision-валидация на компактной мете покрыты
  endpoint-тестом, скан не трогает блоб - структурно (битый блоб).
