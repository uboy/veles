# Решение: из чего собрана база знаний veles и почему каждая часть выбрана

- **Дата:** 07.10.2026
- **Статус:** принято (решение сложилось 26.09-07.10 в ходе постройки и замеров; документ
  фиксирует его по запросу владельца со всеми обоснованиями, цифрами и лицензиями)
- **Повод:** вопрос владельца «почему этот стек, а не встроенный поиск Open WebUI? есть ли
  сравнение, замеры, аргументы за/против?» (скриншот настроек Open WebUI: модель
  paraphrase-multilingual-MiniLM-L12-v2, хранение в YugabyteDB через pgvector, фрагменты
  500/100, гибридный поиск включён)

## 1. Что решаем

База знаний должна отвечать на вопросы по своим документам и показывать, откуда взят
каждый кусок ответа. Требования владельца, зафиксированные в архитектурном стандарте
(docs/ARCHITECTURE.md v3.0):

1. Работает локально, без обязательного облака (облачная модель - вариант, а не основа).
2. Каждый ответ ссылается на первоисточник: файл, раздел, строки.
3. Документы имеют редакции; противоречие редакций - предупреждение, а не молчанка.
4. Пользователи видят разное: личное - только своё, общее - всем.
5. Если ответа в базе нет - честный отказ с причиной, а не выдумка.
6. Качество поиска проверяется замерами, а не ощущениями; новая модель сначала измеряется.
7. Разворачивание на обычной машине без кластеров и администрирования баз данных.

## 2. Два пути

| | Вариант А: встроенный поиск Open WebUI | Вариант Б: собственное ядро veles |
|---|---|---|
| Модель векторов | paraphrase-multilingual-MiniLM-L12-v2 | intfloat/multilingual-e5-small |
| Лимит входа модели | 128 токенов (фрагмент 500 символов обрезается) | 512 токенов |
| Хранение векторов | YugabyteDB через pgvector | NumPy-матрица в памяти + файл |
| Поиск по словам | встроенный гибрид Open WebUI | собственный BM25 + объединение рангов |
| Цитаты | ссылка на прикреплённый файл | документ, редакция, раздел, строки; подписанные ссылки |
| Редакции документов | нет | есть (детектор противоречий) |
| Разграничение пользователей | общая база | есть (личное/общее, поиск от имени пользователя) |
| Честный отказ | нет отдельного | есть (с причиной) |
| Оценка качества | нет | есть: наборы вопросов с эталонами, каждая модель замеряется |
| Свой код | ноль | движок ~несколько тысяч строк + тесты |

## 3. Почему выбран вариант Б: главный аргумент - измерения

Качество поиска измерялось на двух наборах вопросов с эталонными ответами
(57 «золотых» вопросов и 50 вопросов по статьям; замер на стенд, индекс 127 499 фрагментов,
обычный процессор, протокол и первичка - evals/results/k17-artifacts/):

| Набор | Полнота в пятёрке | Точность 1-го места |
|---|---|---|
| Золотой (57) | 0.983 | 0.860 |
| Статьи (50) | 1.000 | 0.600 |

Плюс требуемые функции (редакции, разграничение, цитаты, честный отказ) во встроенном
поиске Open WebUI отсутствуют, а они были в требованиях с самого начала. Проще говоря:
встроенный поиск не проходил бы по нашим же замерам и не умел бы половины заказанного.

Честная цена варианта Б: свой код нужно тестировать и развивать (сейчас 382 автотеста),
а документация и сборка - наша забота. Для сценария «полсотни заметок без требований»
вариант А был бы разумнее - он и рассматривался, и отклонён по функциональным причинам,
не по вкусу.

## 4. Каждая технология: что это, зачем, почему именно она

### 4.1. Модель смысловых векторов: intfloat/multilingual-e5-small

**Что это.** Небольшая нейросеть (33 миллиона параметров), которая превращает текст в
список из 384 чисел так, что похожие по смыслу тексты получают близкие списки. Понимает
русский и ещё ~100 языков. Разработана для поиска: обучалась на парах «запрос - нужный
текст», поэтому перед запросом ставится метка «query:», перед документом «passage:».

**Почему выбрана.**
- Специализирована под поиск, а не под сравнение похожести предложений (как MiniLM).
- Вход до 512 токенов против 128 у MiniLM из настроек Open WebUI: наши фрагменты не
  обрезаются молча (у MiniLM скриншот это подтверждает: «более длинные фрагменты
  обрезаются при вычислении вектора»).
- Замерена на наших вопросах (таблица в разделе 3) - лучший результат из проверенных.
- Работает на обычном процессоре: вектор вопроса - 12 миллисекунд (замер 07.10).
- Крошечная: грузится за секунды, влезает в любой компьютер.

**Кто рассматривался и как отклонён.**
- paraphrase-multilingual-MiniLM-L12-v2 (вариант Open WebUI): модель «похожести
  предложений», не поиска; вход 128 токенов. Прямого замера на нашем корпусе нет
  (замер требует пересборки индекса) - записан открытый пункт в разделе 8.
- EmbeddingGemma 2 (Google, 740 миллионов параметров, мультимодальная): замерена 07.10
  по той же методике - на статьях полнота 0.800 против 1.000 у e5-small, точность ниже
  при 22-кратном размере (evals/results/2026-10-07-eg2-embedding-bench.md). Отклонена.
- Замена модели возможна в любой момент: это отдельная деталь с интерфейсом; главное
  правило - сначала замер, потом внедрение, и при замене пересборка индекса.

**Лицензия:** MIT (свободное использование, включая коммерческое).

### 4.2. Поиск по словам: BM25 (собственная реализация)

**Что это.** Классический алгоритм поиска по ключевым словам (Okapi BM25, 1990-е;
«BM» = Best Matching, «наилучшее совпадение»). Это НЕ нейросеть: обычная формула поверх
индекса «слово -> в каких фрагментах встречается». Работает мгновенно и полностью
объяснимо.

**Зачем он, если есть смысловые векторы.** Векторы находят «по смыслу», но промахиваются,
когда нужны точные слова: артикул «TP-LINK-102», номер договора «Д-23-4567», название
закона, фамилия, аббревиатура. Словесный поиск ловит их намертво. Смысловой и словесный
каналы дополняют друг друга - это и есть гибридный поиск.

**Как работает (простыми словами).** Рейтинг фрагмента по запросу складывается из оценок
его слов, и для каждого слова учитываются три вещи:
1. **Насколько слово редкое во всей базе.** Предлог «и» есть везде и ничего не значит;
   слово «Аркоала» встречается в трёх местах и точно указывает на них. Редкое слово
   даёт много очков, частое - почти ноль.
2. **Сколько раз слово встретилось в этом фрагменте,** с «насыщением»: третья вставка
   слова добавляет меньше очков, чем первая, и когда-то перестаёт добавлять вовсе.
   За это отвечает параметр k1 (у нас 1,5 - стандартное значение).
3. **Длина фрагмента.** Длинный фрагмент не должен выигрывать только потому, что в нём
   больше слов; поправка за длину - параметр b (у нас 0,75, тоже стандарт).

Перед подсчётом текст приводится к нижнему регистру, из него берутся последовательности
букв и цифр (русский алфавит с «ё», латиница, цифры) - так «TP-LINK-102» остаётся целым
словом. Обрезкой окончаний (стеммингом) сознательно не занимаемся: проще и
предсказуемее, а на наших замерах это не мешает.

**Почему собственная реализация, а не готовая библиотека.** Во-первых, она перенесена
из предыдущего проекта, где уже работала (implementation-baseline), - это проверенный
код, а не новая писанина. Во-вторых, нужен был одинаковый разбор текста с векторным
каналом и ноль внешних зависимостей. В-третьих - и главное - польза измерена: в замере
07.10 выключили словесный канал и прогнали те же наборы:

| Набор | С BM25 (гибрид) | Без BM25 (только векторы) |
|---|---|---|
| Статьи: полнота в пятёрке | **1.000** | 0.740 |
| Статьи: точность 1-го места | **0.600** | 0.420 |
| Золотой: полнота в пятёрке | **0.983** | 0.947 |
| Золотой: точность 1-го места | **0.860** | 0.702 |

Словесный канал добавляет до 26 процентных пунктов полноты на статьях и 16 пунктов
точности на золотом наборе. Это и есть ответ «зачем BM25» цифрами, а не вкусом.

**Где живёт.** veles/indexing (построение) и veles/retrieval (поиск); словесный индекс
хранится рядом с векторами в обычном файле JSON.

**Лицензия:** собственный код в составе veles.

### 4.3. Объединение двух каналов: взаимный ранг

**Что это.** Смысловой канал даёт свой список фрагментов, словесный - свой. Места в этих
списках несравнимы напрямую (разные шкалы). Поэтому каждый фрагмент получает очки в
каждом списке по формуле «1 / (60 + место)», очки складываются, список пересортируется.
Константа 60 - стандартная, сглаживает разницу первых мест.

**Почему так.** Это устойчиво (не зависит от того, что один канал всегда даёт оценки по-
крупнее), просто, и на наших замерах связка «векторы + слова + взаимный ранг» дала
приведённые выше цифры. Усилители (например, прибавка веса фрагментам-родителям) и
переклассификатор верхних результатов (модель, которая перетасовывает первую пятёрку)
в архитектуре предусмотрены, но сейчас выключены: замедляют ответ, а польза на наших
наборах не показана. Это точки роста, а не недоделки.

**Лицензия:** собственный код.

### 4.4. Хранение векторов: NumPy-матрица в памяти

**Что это.** Все векторы базы - одна прямоугольная таблица чисел (файл на диске, при
старте загружается в память). Поиск - полный перебор: вектор запроса умножается на
каждую строку, берутся лучшие. Без серверов, без баз данных, без администрирования.

**Почему выбрано.**
- Скорость достаточна с запасом: поиск по 127 500 фрагментам - ~193 миллисекунды на
  обычном процессоре (замер 07.10); база из 231 тысячи фрагментов весит 1,3 ГБ.
- Ноль зависимостей: кит разворачивается как «докер + каталог с данными», никаких
  баз данных ставить и бэкапить отдельно не нужно.
- Полный перебор даёт ГАРАНТИЮ наилучшего результата по векторам: приближённые
  алгоритмы (специальные индексы) ускоряют поиск ценой возможных пропусков - нам
  ускорять пока некуда, а точность терять рано.

**Почему НЕ YugabyteDB + pgvector (вариант Open WebUI).** YugabyteDB - распределённый
кластер баз данных: он придуман для десятков машин и терабайтов и несёт за это цену -
требователен к памяти, его нужно разворачивать, обновлять и бэкапить как отдельный
сервис. Для персональной базы на одной машине это огромная цена за то, что матрица в
памяти делает быстрее и без единой строчки настройки. Порог, где векторная база
действительно нужна (сотни миллионов фрагментов, много одновременных пользователей),
нашему сценарию не грозит; а если грозил бы - в архитектуре предусмотрен интерфейс
хранилища, и Qdrant (рассматривался, адаптер написан в предшественнике) встаёт без
переписывания поиска.

**Лицензии:** NumPy - BSD-3; Qdrant - Apache-2.0; pgvector - свободная лицензия
PostgreSQL; ядро YugabyteDB - Apache-2.0.

### 4.5. Библиотека эмбеддингов: sentence-transformers

**Что это.** Стандартная свободная библиотека для загрузки и запуска векторных моделей
на процессоре и видеокарте. Берёт на себя разбиение на партии, ускорители и нормировку.

**Почему выбрана.** Де-факто стандарт с готовыми моделями; у моделей e5 и Gemma в её
терминах описаны промпты для запроса и документа - мы используем их ровно как
предписано (это проверялось при замере EmbeddingGemma 2: правильные метки запросов и
документов, нормировка, укорачивание вектора до нужной длины с пересуммированием).

**Лицензия:** Apache-2.0.

### 4.6. Модель ответов: gemma-4-31b на видеокарте V100 через llama.cpp

**Что это.** Языковая модель, которая получает найденные фрагменты и пишет по ним
связный ответ со ссылками. Работает на сервере с видеокартой V100 (32 ГБ) через
llama.cpp - программу, которая запускает такие модели локально и отдаёт стандартный
интерфейс, как у облачных.

**Почему выбрана.**
- Бесплатный внутренний ресурс вместо облачной подписки (решение владельца 07.10:
  «пользуемся бесплатной; не у всех есть возможность использовать облачные модели»).
- Модель не участвует в поиске и индексации: её можно заменить, выключить или
  переехать на другой компьютер - база и поиск не замечают этого (проверено 07.10:
  сервер ответов поднимали заново на том же порту, фасад не потребовал ни одной правки).
- Квантованная версия (сжатая с 4 битами на вес) влезает в 32 ГБ видеокарты целиком
  с запасом на длинные тексты (~26,5 ГБ занято).

**Лицензии:** llama.cpp - MIT; gemma - собственная свободная лицензия Google (Gemma
Terms of Use): бесплатное использование с оговорками.

### 4.7. Сервис-фасад: FastAPI

**Что это.** Тонкий слой поверх движка: принимает вопросы и загрузки документов,
проверяет права, отдаёт ответы с цитатами и подписанные ссылки на источник.

**Почему свой, а не «прямо из Open WebUI».** Потому что в фасаде живёт именно то, чего
нет во встроенном поиске: редакции документов, разграничение доступа (поиск от имени
конкретного пользователя), подписанные ссылки с сроком действия, честный отказ,
честные статусы загрузки («сервис перезапускался - задание не завершилось, повторите»).

**Лицензия:** FastAPI - MIT.

### 4.8. Интерфейс: Open WebUI

**Что это.** Готовый веб-чат (истории, пользователи, вложения). Используется ТОЛЬКО как
интерфейс: к нему подключена одна функция «База знаний (veles)», которая зовёт наш фасад
и рисует ответ с цитатами.

**Почему не его встроенный поиск** - см. разделы 2-3. **Почему оставили его как
интерфейс:** готовый, знакомый пользователям, экономит месяцы работы над чатом.

**Лицензия:** собственная свободная лицензия Open WebUI (на основе BSD-3, с оговоркой
о сохранении фирменного оформления для крупных компаний; для нашего использования
несущественно).

### 4.9. Проверка качества как часть стека

Наборы вопросов с эталонами (57 «золотых» + 50 по статьям + 470 по вики OpenHarmony,
добавленный 07.10) - такая же часть системы, как код: любая новая модель или настройка
поиска сначала прогоняется на них, и решение принимается по цифрам (свежие примеры:
отклонение EmbeddingGemma 2, измеренная польза BM25 в разделе 4.2). Без этого
обоснование стека выглядело бы как вкусовщина.

## 6. Лёгкость разворачивания

- **veles (выбрано):** архив кода ~400 КБ + docker compose + сценарий установки с
  вопросами; данные - один каталог; обновление = новый кит + перенос каталога.
  Полная инструкция для новой машины: docs/DEPLOY-NEW-MACHINE.md.
- **вариант Open WebUI + YugabyteDB:** сам Open WebUI ставится так же просто, но
  YugabyteDB - кластерный продукт (минимум избыточен на одной машине, требователен
  к памяти), плюс конфигурация Open WebUI хранится в своей базе и может расходиться
  с настройками из файла окружения (это видно и на скриншоте настроек).
- **Урок 07.10:** узкое место развёртывания - не поиск и не модель, а ОЗУ хоста: на
  машине с 7 ГБ индексация толстых книг при перезаписи файлов индекса доедает память
  до перезапуска сервиса (за день три таких случая). Рекомендация в кит: машина от
  16 ГБ или файл подкачки +4 ГБ.
