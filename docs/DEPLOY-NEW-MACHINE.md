# Развёртывание Veles с нуля на отдельной машине (вручную, по шагам)

Путь для корпоративного контура: одна Linux-машина, docker, WebUI + фасад в
контейнерах, данные организации грузятся админом через API (общие), личные
документы пользователи кидают в чат. Путь отработан: сервер (демо, jwt) и стенд.

Время: ~30-40 минут до первого ответа, из них ~10 минут - скачивания.
Нужны: Ubuntu 20.04+ (проверено 22.04/24.04), 2+ ядра, 8+ ГБ RAM, 20+ ГБ диска,
доступ к LLM (OpenAI-совместимый URL), доступ к huggingface.ru на первом старте.

---

## Шаг 0. Получить дистрибутив (кит)

Кит собирается из репозитория (доступ - по приглашению в private-репозиторий
github.com/uboy/veles). На машине с репозиторием:

```bash
bash deploy/kit/make-kit.sh                 # соберёт veles-deploy-kit-<версия>.tar.gz
```

Переложить архив на целевую машину (scp/флешка) и распаковать:

```bash
tar xzf veles-deploy-kit-<версия>.tar.gz
cd veles-deploy-kit-<версия>/deploy/kit
```

Альтернатива без кита: `git clone` репозитория и тот же путь `deploy/kit`.

## Шаг 1. Установить docker (если нет)

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER && exec su - $USER    # перелогиниться
docker compose version                               # проверить плагин compose
```

## Шаг 2. Установщик: профиль corporate

```bash
./install.sh --profile corporate --with-webui --yes
```

`--yes` берёт дефолты вместо вопросов там, где это безопасно. На вопросы
установщика ответить (значения пишутся в `.env`, всё можно поменять потом
и перезапустить `docker compose up -d`):

| Вопрос | Что ответить |
|---|---|
| Публичный URL фасада | `http://<IP-или-имя-машины>:8400` - адрес, по которому пользователи откроют ссылки на источники. НЕ 127.0.0.1 |
| Общие группы доступа | `all` (именно так: это группы, видимые ВСЕМ пользователям; не пишите тут personal) |
| Режим личности | jwt (дефолт corporate, не менять) |
| Админы (email) | ваш рабочий email, например `ivanov@company.ru` - по нему WebUI-аккаунт получит права админа базы |
| Базовый URL LLM | OpenAI-совместимый эндпоинт; локальный llama.cpp: `http://<llm-хост>:8471/v1`, облако - URL провайдера |
| Модель LLM | имя модели у провайдера (наши стенды: `gemma-4-31b-it`) |
| Ключ LLM | ключ провайдера (пишется в .env без эха; для локального llama.cpp - любой непустой) |

Установщик сам сгенерирует: `VELES_API_TOKEN` (служебный ключ фасада),
`VELES_LINK_SECRET` (подписи ссылок в цитатах), `WEBUI_SECRET_KEY`,
`VELES_IDENTITY_JWT_SECRET` (подписанные заголовки WebUI→фасад).

## Шаг 3. Поднять и дождаться готовности

```bash
docker compose up -d
docker compose ps                          # veles-facade и open-webui - Up
curl -s http://127.0.0.1:8400/healthz      # {"status":"ok",...}
curl -s http://127.0.0.1:8400/readyz       # 200 когда фасад готов (пустая база готова сразу)
```

Open WebUI: `http://<машина>:8300`.

## Шаг 4. Создать админа в WebUI

1. Открыть `http://<машина>:8300`, «Зарегистрироваться».
2. Email - В ТОЧНОСТИ тот, что в `VELES_ADMIN_EMAILS` из `.env`.
   Первый зарегистрированный аккаунт становится админом WebUI; совпадение
   email даёт ему админа базы (wildcard, видит всё).
3. Саморегистрацию закрыть: Admin Panel → Settings → General →
   «Enable New Sign Ups» = выкл. (в контейнере уже `ENABLE_SIGNUP=false`,
   проверьте переключатель в UI). Новых пользователей создаёт админ:
   Admin Panel → Users → «+» (email, имя, временный пароль).

## Шаг 5. Подключить единую модель «База знаний (Veles)»

Модель - это функция-прослойка: файл из чата падает в личное хранилище
пользователя, вопрос идёт в базу от имени этого пользователя.

1. Admin Panel → Functions → «+» → вставить содержимое
   `integrations/openwebui/functions/veles_knowledge.py` из кита → Save.
2. Модель включить (тумблер) и убедиться, что она появилась в списке моделей
   чата как «База знаний (Veles)».
3. Valves функции (значок шестерёнки): `veles_url` = `http://veles-facade:8400`
   (имя сервиса compose), `veles_token` = `VELES_API_TOKEN` из `.env`,
   `veles_public_url` = тот же публичный URL, что в Шаге 2.
4. Старые прочие модели (OpenAI-коннекторы, Arena) - выключить в Admin Panel →
   Settings → Connections, чтобы в чате осталась одна модель.

## Шаг 6. Загрузить стартовые данные организации (админ)

Данные, которые должны видеть ВСЕ, грузятся через API с группой `all`
(чат-загрузка админа кладёт файлы в его ЛИЧНОЕ хранилище - для общих данных
не годится). Из каталога кита:

```bash
TOKEN=$(grep -oP '^VELES_API_TOKEN=\K.*' .env | tr -d '"')

# один файл:
curl -s -X POST http://127.0.0.1:8400/v1/documents \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@/путь/Регламент_отпусков.pdf" -F "group=all" -F "title=Регламент отпусков"

# папка документов (txt/md/pdf; для docx - пересохранить в pdf или txt):
for f in /путь/корпус/*; do
  curl -s -X POST http://127.0.0.1:8400/v1/documents -H "Authorization: Bearer $TOKEN" \
    -F "file=@$f" -F "group=all" >/dev/null && echo "ok $f"
done
```

Обработка очереди - на слабой машине ~минуты на десяток файлов. Готовность и
ошибки: `curl -s http://127.0.0.1:8400/v1/documents/jobs/<job_id> -H "Authorization: Bearer $TOKEN"`
(ждать `done`). Проверка, что документ находим:

```bash
curl -s -X POST http://127.0.0.1:8400/v1/knowledge/query \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"query":"<фраза из документа>","top_k":3,"use_llm":false}' | grep -o '"decision": "[a-z]*"'
```

Данные для ОТДЕЛА (не всей организации): создать серверную группу
`<данные>/groups.json` (см. «Группы доступа» в deploy/kit/README.md), внести
в неё сотрудников, грузить с `-F "group=<id-группы>"`.

## Шаг 7. Пользователи: как работают и как проверить разграничение

Пользователь заходит в WebUI, выбирает модель «База знаний (Veles)»:

- **вопрос текстом** - ответ по базе с кликабельными цитатами (видит общие
  данные и СВОИ личные; чужое личное не находится);
- **прикрепил файл** - уйдёт в его личное хранилище, станет находим только ему;
- **файл + вопрос** - загрузит и ответит одним сообщением;
- вопрос не по базе - честный «ответа в базе нет».

Проверка разграничения (2 пользователя, 5 минут):
1. Пользователь A прикладывает в чат файл с уникальной фразой (например
   «квота компостирования 47 кг»), ждёт подтверждения загрузки.
2. Пользователь B спрашивает ту же фразу → должен получить «ответа в базе нет».
3. Админ спрашивает ту же фразу → находит (админ видит всё).

Если B видит документ A - стоп, проверить: email A и B разные, оба не админы
(`VELES_ADMIN_EMAILS`), модель обновлена до версии с K21 (в файле функции есть
строка K21).

## Шаг 8. Бэкапы (сразу настроить)

Всё состояние - в одном каталоге: `deploy/kit/data` (канон + индекс + очередь)
и `.env` (секреты). Ежедневный ночной архив:

```bash
sudo tee /etc/cron.d/veles-backup > /dev/null <<'EOF'
30 3 * * * <пользователь> tar czf /home/<пользователь>/veles-backups/veles-$(date +\%F).tar.gz -C <путь-к-киту>/deploy/kit data .env && find /home/<пользователь>/veles-backups -name 'veles-*.tar.gz' -mtime +7 -delete
EOF
mkdir -p ~/veles-backups
```

(`<пользователь>` и `<путь-к-киту>` заменить на свои; проверка: `sudo run-parts --test /etc/cron.d` и один ручной запуск команды из cron.)

Восстановление: остановить `docker compose down`, распаковать архив поверх
`deploy/kit/`, `docker compose up -d`.

## Шаг 9. Обновление версии

```bash
# новая версия кита → распаковать рядом, перенести data/ и .env, затем:
docker compose build && docker compose up -d
# база переживёт: очереди джобов и канон на диске, индекс подхватывается как есть
```

Правка функции WebUI при обновлении: Admin Panel → Functions →
veles_knowledge → вставить новый файл → Save.

## Неисправности

- **readyz 503** - индекс ещё грузится (на слабой машине 2-5 минут; на 127 тыс.
  узлов стенд грузится за 13 с, сервер за ~3 мин). Подождать, не рестартить в цикле.
- **«Фасад отклонил токен (401)» в чате** - Valve `veles_token` не совпадает
  с `VELES_API_TOKEN` из `.env`.
- **В ответе приписка «Синтез нейросетью временно недоступен»** - LLM-хост
  не отвечает (проверить `VELES_LLM_BASE_URL`/`VELES_LLM_API_KEY` в .env;
  после правки `docker compose up -d`).
- **«Ответа на этот вопрос в базе знаний нет»** - документ не загружен, не в
  группе пользователя или ещё обрабатывается (очередь: /v1/documents/jobs/<id>).
- **Ссылки-цитаты не открываются** - `VELES_PUBLIC_URL` не виден с машины
  пользователя (127.0.0.1 вместо реального адреса).
- **Пользователь видит «пустую базу»** - он не в группах, где лежат документы:
  общие данные грузятся с `group=all`, отделы - через groups.json (Шаг 6).
