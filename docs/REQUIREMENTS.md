# Требования к разворачиванию и масштабированию

Дата: 2026-10-08. Все цифры - из замеров, у каждой указано, где и на чём
измерено; оценочные значения помечены. Связанные документы:
`docs/adr/2026-10-07-vybor-steka-bazy-znaniy.md` (стек и граница
применимости), `docs/DEPLOY-NEW-MACHINE.md` (порядок разворачивания).

## Профили разворачивания

### 1. Минимальный: текстовый поиск без синтеза (малый корпус)

Для базы до ~20 тыс. узлов (несколько десятков документов) - оценка,
экстраполяция от измеренного среза:

- CPU: 2 ядра x86-64 (поиск и кодирование запросов идут на CPU)
- RAM: 4 ГБ
- Диск: 10 ГБ SSD (данные + модели + docker-образы)
- Сеть: доступ к huggingface.co только на этапе сборки индекса

### 2. Текущий производственный срез (127 498 узлов, 390 документов)

Измерено на живом сервисе (одноядерный хост с 7 ГБ RAM, docker stats
08.10.2026) и в замере латентности от 07.10.2026:

- CPU: 4 ядра x86-64
- RAM: 8 ГБ (фасад целиком - 3.93 ГиБ; веб-интерфейс - ~55 МБ;
  меньше 7 ГБ на хосте - впритык, свободным остаётся ~2 ГБ)
- Диск: 20 ГБ SSD (каталог данных 2.1 ГБ: индекс 1.3 ГБ + канон
  368 МБ + пользовательские загрузки 370 МБ; модель эмбеддера ~450 МБ)
- Латентность: гибридный поиск 193 мс на CPU при 127 499 узлах,
  кодирование запроса эмбеддером 12 мс (первичка:
  `evals/results/2026-10-07-ablation-dense-only/summary.json`)
- Синтез ответов на этом профиле - только внешний LLM-endpoint

### 3. С синтезом ответов (LLM)

- Вариант «без GPU»: любой OpenAI-совместимый endpoint (фасад вызывает
  его по HTTP); данные наружу уходят только в этот endpoint - это
  надо учитывать в контуре доверия
- Вариант self-host: модель 30B-класса в 4-битном квантовании - около
  20 ГБ видеопамяти (у нас: gemma-4-31b-it Q4_K_M на GPU 32 ГБ);
  LLM на CPU даст минуты на ответ - не рекомендуется

### 4. Картинный канал (опционально, выключен по умолчанию)

- Сборка индекса картинок: разовая операция, GPU желательна
  (30 картинок: 2.7 с на GPU против 116 с на CPU int8, замер 08.10);
  готовый каталог индекса переносится на хост сервиса
- Кодировщик запросов живёт рядом с фасадом и ест память: полная
  модель 4.4 ГБ, динамическое int8-квантование 3.0 ГБ установившейся
  памяти (замер 08.10, первичка
  `evals/results/2026-10-08-image-channel-bench.md`). На профиле 2
  (8 ГБ) не влезает - нужен хост с 16 ГБ либо вынос кодировщика на
  отдельную машину; статическое ONNX-квантование (оценка ~1.2-1.5 ГБ)
  пока не сделано

## Требования к серверной части (софт)

- ОС: Linux x86-64 с Docker и docker compose (деплой-кит);
  на Windows - запуск из исходников для разработки
- Порты: 8400 (API фасада), 8300 (веб-интерфейс); наружу они
  публиковаться не обязаны (см. DEPLOY-NEW-MACHINE)
- Транспорт моделей: huggingface.co на момент сборки/пересборки индекса
- Пересборка индекса - офлайн-операция (на 127 тыс. узлов - часы,
  CPU); каталог данных переносим между машинами, сборку можно делать
  на машине с GPU и довозить готовый индекс
- При пересборке на месте - свободное место примерно вдвое против
  объёма каталога данных (снимок + дописывание)

## Модели: требования и размеры

| Роль | Модель | Размер | Где работает |
|---|---|---|---|
| Эмбеддер текста (обязательная) | multilingual-e5-small, ~118M параметров | ~450 МБ | CPU, обрезка входа 512 токенов |
| Эмбеддер-кандидат (замер 08.10) | Qwen3-Embedding-0.6B | ~1.2 ГБ | пересборка индекса - GPU; обязательна обрезка 512 токенов для сопоставимости с e5 |
| Картинная модель (опция) | jina-clip-v2, 0.9B | 3.5-4 ГБ | сборка - GPU; запросы - CPU 3-4.4 ГБ RAM |
| LLM синтеза (опция) | 30B-класс, 4-бит | ~20 ГБ VRAM | GPU-хост или внешний endpoint |

## Масштабирование: что растёт с корпусом

- Плотные векторы: 1.5 КБ на узел (384 измерения, float32) - в RAM и на
  диске (127 498 узлов = 196 МБ, измерено)
- Лексический индекс: ~0.9 КБ на узел на диске (113 МБ); в RAM фасада
  занимает основную часть потребления сверх векторов
- Латентность поиска растёт линейно (полный перебор): 193 мс при 127 тыс.
  узлов; около миллиона узлов - ожидание порядка 1.5 с (экстраполяция),
  дальше нужен индекс с алгоритмической выборкой (IVF/HNSW) - в коде
  предусмотрена замена бэкенда
- RAM фасада растёт примерно линейно по узлам; ориентир: 8 ГБ хост
  держит ~150 тыс. узлов, 16 ГБ - порядка 400-500 тыс. (оценка)
- Канон с исходными текстами и картинками: ~1 МБ на документ
  (368 МБ на 390 документов)
- Индексация: очередь до 50 задач; тяжёлый разбор PDF держит память
  (парсер) - большие партии лучше гнать на отдельной машине
- Горизонтально: каталог данных переносим; несколько экземпляров
  сервиса масштабируются шардингом по коллекциям/группам доступа;
  LLM-endpoint один на несколько фасадов

## Известные границы

- Хост с 7 ГБ RAM (текущий сервис): живёт впритык, картинный канал не
  влезает - пример нижней границы комфортного профиля
- Индекс без алгоритмической выборки: комфортно до нескольких сотен
  тысяч узлов на 16 ГБ RAM, дальше - IVF/HNSW или шардинг
