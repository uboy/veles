# Требования к разворачиванию и масштабированию

Дата: 2026-10-08 (редакция 2 - обычный язык вместо внутренних терминов).
Все цифры - из замеров, у каждой указано, где и на чём измерено; оценочные
значения помечены. Связанные документы:
`docs/adr/2026-10-07-vybor-steka-bazy-znaniy.md` (выбор технологий),
`docs/DEPLOY-NEW-MACHINE.md` (порядок разворачивания).

Из чего состоит система:

- **API-сервер** - программа, которая хранит индекс по документам и отвечает
  на вопросы: сам ищет нужные места и (если настроено) составляет ответ с
  помощью языковой модели. Занимает оперативную память под индекс.
- **Веб-интерфейс** - страница чата для человека (почти не тратит память).
- **Языковая модель** - отдельно стоящая программа (или облачный сервис),
  к которой API-сервер обращается по сети, чтобы составлять ответы.
  База знаний работает и без неё - тогда отвечает цитатами из документов.

## Профили разворачивания

### 1. Минимальный: поиск по тексту, небольшой корпус

Для базы до ~20 тыс. фрагментов (несколько десятков документов) - оценка,
экстраполяция от измеренного среза:

- Процессор: 2 ядра x86-64 (поиск и подготовка запросов идут на процессоре)
- Память: 4 ГБ
- Диск: 10 ГБ SSD (данные + модели + docker-образы)
- Сеть: доступ к huggingface.co нужен только при сборке индекса

### 2. Текущий рабочий объём (127 498 фрагментов, 390 документов)

Измерено на работающем сервисе (хост с 7 ГБ памяти, docker stats 08.10.2026)
и в замере скорости от 07.10.2026:

- Процессор: 4 ядра x86-64
- Память: 8 ГБ (API-сервер целиком - 3.93 ГиБ; веб-интерфейс - ~55 МБ.
  На хосте с 7 ГБ живёт впритык: свободным остаётся ~2 ГБ)
- Диск: 20 ГБ SSD (данные 2.1 ГБ: индекс 1.3 ГБ + тексты с картинками
  368 МБ + пользовательские загрузки 370 МБ; модель поиска ~450 МБ)
- Скорость: поиск 193 мс на процессоре при 127 499 фрагментах, подготовка
  вопроса 12 мс (первичка:
  `evals/results/2026-10-07-ablation-dense-only/summary.json`)
- Составление ответов на этом профиле - только через внешнюю языковую
  модель по сети

### 3. С составлением ответов (языковая модель)

- Без своей видеокарты: любая модель за HTTP по OpenAI-совместимому
  протоколу (облачный сервис или отдельная машина в сети). База знаний
  общается с ней по адресу и ключу - ровно как любой ChatGPT-клиент.
  Учитывайте в контуре доверия: тексты вопросов и найденных цитат уходят
  к этой модели.
- Со своей видеокартой: модель 30-миллиардного класса в 4-битном сжатии
  занимает около 20 ГБ видеопамяти (у нас: gemma-4-31b-it в Q4_K_M на
  карте с 32 ГБ). Языковая модель на одном процессоре отвечает минутами -
  не рекомендуется.

### 4. Поиск по изображениям (дополнение, по умолчанию выключено)

- Сборка индекса картинок - разовая операция, желательно на видеокарте
  (30 картинок: 2.7 с на видеокарте против 116 с на процессоре, замер
  08.10); готовый индекс переносится на хост сервиса файлами.
- Кодировщик запросов живёт рядом с API-сервером и занимает память:
  полная модель 4.4 ГБ, сжатая до 8 бит - 3.0 ГБ (замер 08.10, первичка
  `evals/results/2026-10-08-image-channel-bench.md`). На профиле 2 (8 ГБ)
  не помещается - нужен хост с 16 ГБ либо отдельная машина. Более сильное
  сжатие (формат ONNX, оценка 1.2-1.5 ГБ) пока не сделано.

## Требования к серверной части (софт)

- ОС: Linux x86-64 с Docker и docker compose (готовый комплект
  разворачивания); на Windows - запуск из исходников для разработки.
- Порты: 8400 (API), 8300 (веб-интерфейс); наружу их публиковать не
  обязательно (см. DEPLOY-NEW-MACHINE).
- Доступ к huggingface.co - при сборке и пересборке индекса (загрузка
  моделей).
- Пересборка индекса - отдельная фоновая операция (на 127 тыс. фрагментов -
  часы на процессоре). Каталог данных переносим между машинами: можно
  собрать индекс на быстрой машине и привезти готовый.
- При пересборке на месте нужно свободное место примерно вдвое против
  объёма данных.

## Модели: требования и размеры

| Роль | Модель | Размер | Где работает |
|---|---|---|---|
| Поиск по тексту (обязательная) | multilingual-e5-small, ~118M параметров | ~450 МБ | процессор, вход до 512 токенов |
| Кандидат на замену (замер 08.10) | Qwen3-Embedding-0.6B | ~1.2 ГБ | пересборка индекса - видеокарта |
| Поиск по картинкам (дополнение) | jina-clip-v2, 0.9B | 3.5-4 ГБ | сборка - видеокарта; запросы - процессор, 3-4.4 ГБ памяти |
| Составление ответов (дополнение) | 30B-класс в 4 битах | ~20 ГБ видеопамяти | видеокарта или внешний сервис по сети |

## Масштабирование: что растёт с корпусом

- Векторы поиска по смыслу: 1.5 КБ на фрагмент (384 числа) - в памяти и
  на диске (127 498 фрагментов = 196 МБ, измерено).
- Поиск по словам: ~0.9 КБ на фрагмент на диске (113 МБ); в памяти
  API-сервера занимает основную часть сверх векторов.
- Скорость поиска падает линейно с ростом корпуса (полный перебор): 193 мс
  при 127 тыс. фрагментов; около миллиона - ожидание порядка 1.5 с
  (экстраполяция); дальше нужен индекс с выборкой (IVF/HNSW) - в коде
  предусмотрена замена этого механизма.
- Память API-сервера растёт примерно линейно; ориентир: 8 ГБ хост держит
  ~150 тыс. фрагментов, 16 ГБ - порядка 400-500 тыс. (оценка).
- Тексты и картинки документов: ~1 МБ на документ (368 МБ на 390).
- Загрузка новых документов: очередь до 50 задач; разбор больших PDF
  расходует память - крупные партии лучше обрабатывать на отдельной
  машине.
- По горизонтали: каталог данных переносим; несколько экземпляров сервиса
  масштабируются разделением коллекций и групп доступа; одна языковая
  модель может обслуживать несколько экземпляров базы.

## Известные границы

- Хост с 7 ГБ памяти (текущий сервис): поиск по тексту работает, но
  свободный запас ~2 ГБ - поиск по изображениям и кандидат на замену
  модели поиска туда не помещаются. Это пример нижней границы.
- Индекс без алгоритмической выборки: комфортно до нескольких сотен тысяч
  фрагментов на 16 ГБ памяти, дальше - IVF/HNSW или разделение корпуса.
