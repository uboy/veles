## 1. Механизм вывода из поиска: tombstone, не перезапись бандла

Выбран **live tombstone-патч** (status=deleted в мете узлов + тот же патч в
overlay). Основания по коду:

1. `NumpyFlatStore`/`FaissFlatStore` и `Bm25Index` — append-only (`add`), API
   удаления нет: физический вывод узлов = пересборка обеих структур в памяти и
   полная перезапись бандла на диск.
2. `IndexBundle.save()` стирает overlay.npz — а в нём лежат дельты ДРУГИХ
   документов, загруженных после последней пересборки (K4). Перезапись бандла
   ради одного удаления либо теряет чужие дельты, либо требует слияния overlay
   в бандл — дорогой и рискованный путь ради операции, которая и так
   самоустраняется при плановой пересборке.
3. Tombstone — тот же механизм, что уже работает для superseded-ревизий (K3):
   патч поля status в мете, O(узлов документа), атомарен для читателей
   (обновление полей dict под GIL, как в upsert_document), персистентен через
   overlay (fsync+replace, K8) и **самоликвидируется** при полной пересборке:
   канон уже в trash, `iter_documents` его не видит, `bundle.save` стирает
   overlay. Цена: вектор/BM25-записи узлов лежат в бандле до пересборки
   (память не освобождается) — приемлемо, удаление редкое.

Клейм tombstone-патча: **безусловный** фильтр `status == "deleted"` в
`hybrid_search.authorized()` ДО групповой и ревизионной проверок — иначе
`revision="all"` и `revision="r<n>"` обходили бы tombstone (там статус
не проверяется вовсе). Админ с `*` удалённое тоже не видит. `knowledge_stats`
пропускает deleted во всех счётчиках (не в superseded_nodes).

Два сопутствующих фикса, без которых tombstone не работал бы честно:

- `_apply_checked` делал ранний `return` при пустом `ids` — overlay,
  содержащий ТОЛЬКО патчи (tombstone документа из основного индекса, векторов
  0), молча не применялся при загрузке, и после рестарта документ всплывал до
  пересборки. Теперь мета+патчи применяются всегда, `return` отсекает только
  векторную часть (тем самым закрыт и latent-случай K4 «дельта без
  индексируемых узлов»).
- `append_overlay` при переиздании узла сбрасывает его stale-патч: повторная
  загрузка того же текста после удаления даёт ТЕ ЖЕ node_version_id
  (`sha256(revision_id|logical_node_id|text)`), и старый tombstone-патч
  переживал бы новую мету при рестарте — переизданный документ навсегда
  исчезал бы из поиска. Патчи superseded не задеты: они целятся в id
  предыдущей ревизии, у новых узлов id другие.

ACL удаления: владелец (`user:<uid>` ∈ access_groups манифеста) или админ
(`admin`-флаг или `*` — та же трактовка, что `_visible_by_groups`); член
серверной группы с правом чтения удалять НЕ может. Чужой и несуществующий —
одинаковый 404 `«документ не найден»`, без личности — 401 (тот же
`identity_fn`, что у query/chat). Guard обхода каталогов: doc_dir обязан быть
прямым потомком каталога канона (`_doc_dir` пропускает `.`/`..`, а удаление —
разрушительная операция).

## 2. Проверка (pytest, tests/test_delete.py — 8 кейсов)

Позитив: владелец удаляет свой (полный цикл), админ и bearer-владелец — любой,
static-владелец — свой; tombstone узла ОСНОВНОГО индекса (корпусный документ).
Негативы (падают по своей причине): чужой — 404 (деталь совпадает с
несуществующим — неотличимость), double-delete — 404, без личности — 401,
CLI без --yes — код 1 и канон не тронут.

Покрыто: поиск закрывается СРАЗУ (default + revision=all + revision=r1, у
владельца/админа/bearer); source/asset → 404; stats.totals.nodes уменьшились
ровно на nodes из ответа DELETE, документа нет в оглавлении; L0 удалён;
trash-каталог `<ts>-<имя>` с manifest.json + nodes.jsonl + trash-meta.json
(document_id, deleted_by); все ревизии (r1 архив + r2 текущая) в trash вместе
и не ищутся ни в одном revision-режиме; аудит-событие `delete` в
ingest-audit.jsonl (by, document_id, trash); рестарт (`load_index` = overlay
применён) документ не возвращает; полная пересборка (`build_index` + `save` +
`load_index`) не возвращает, соседний/засеянный документ жив; квота
освобождается сразу (VELES_QUOTA_DOCS=1: отказ → delete → загрузка проходит);
re-upload того же текста ищется сразу И после рестарта (regression сброса
stale-патча); CLI `veles delete [--yes]` — план без --yes, удаление с --yes,
tombstone собран с диска (bundle=None: meta.json + overlay) и виден после
`load_index`.

Пояснение к отрицательному CLI-кейсу: без `--yes` команда выходит с кодом 1,
печатает план и НЕ вызывает delete_document — тест фиксирует, что канон и
поиск не тронуты (не «зелёный по совпадению»: без проверки manifest.json на
месте кейс не отличил бы «план» от «удаления»).

## 3. Мини-E2E на стенд (порт 18450, tmp VELES_DATA)

Сценарий: seed корпусного документа → build_index настоящим эмбеддером →
старт фасада → загрузка «Договор поставки» через POST /v1/documents (джоб
done) → поиск находит (decision=answer, 1 цитата) → DELETE → 200
(`nodes:1, revisions:[r1], trash:[20260929T111034-owner_Договор_поставки.md]`)
→ поиск abstain, 0 цитат → trash на диске (manifest/nodes/trash-meta), L0
удалён, аудит-событие delete → double-delete 404 → рестарт фасада → Б не
всплывает (abstain) → `python -m veles index` (пересборка: 1 узел — только
соседний А) → рестарт → Б не всплывает, А жив (answer, 1 цитата).

Инцидент в ходе E2E (зафиксирован честно): первые «зелёные» прогоны били в
**осиротевший процесс фасада** от прерванного запуска, продолжавший держать
порт 18450 — шаги «рестарт» и «пересборка» обслуживались старым процессом с
загруженным один раз индексом, то есть НЕ проверялись. Урок: скрипт E2E обязан
проверять, что порт отвечает именно запущенному им pid. Исправлено: скрипт
гасит чужих слушателей 18450 перед стартом и после readyz сверяет
`ss -tlnp` c `serve.pid` (FAIL, если порт держит чужой). Финальный прогон с
этой проверкой — все шаги зелёные, включая рестарт и пересборку; после
очистки порт свободен, процессов нет.

## 4. Не проверено

- Восстановление из trash вручную (перенос каталога назад + пересборка) —
  restore вне фазы; путь описан в DEPLOY-стенд.md, но не прогнан.
- Гонка «DELETE против идущего джоба ингеста того же document_id» — сознательно
  не закрывалась (комментарий в роуте); одновременный DELETE+POST не
  нагрузочным тестом.
- Много-корневой VELES_DATA (несколько canonical*) в проде: код удаляет из
  всех корней (как чтение), но в E2E/тестах корень один.
- Освобождение памяти бандла (векторные записи удаённых узлов лежат до
  пересборки) — по дизайну tombstone; эффект на проде (158k узлов) не
  замерялся.
- rate-limit (K6) на DELETE отдельно не проверялся — роут проходит общий
  install_rate_limit; в тестах лимиты не задевались.
