## Что сделано

- **API** (`veles/api/documents.py`): `POST /v1/documents` - multipart (file +
  title, access_groups) или JSON ({text, title}); 202 {job_id, status, document_id}.
  `GET /v1/documents/jobs` (свои; админ - все) и `GET /v1/documents/jobs/{id}`
  (чужой = 404, не палит чужие загрузки). Форматы: txt/md/pdf (pdf - docling).
  app.py - только `include_router` и шов `state["identity_fn"]/["pipeline_fn"]`
  в `app.state.veles` (9 добавленных строк, 0 изменённых - файл для K6 не перекроен).
- **Очередь** (`veles/ingest/queue.py`): одна последовательная фоновая очередь в
  процессе фасада; джобы в памяти + append-журнал `uploads/ingest-jobs.jsonl` с
  boot-id. **Рестарт-семантика**: при чтении статуса джоб чужого boot_id со
  статусом queued/running честно переводится в failed «сервис перезапущен, задание
  не завершилось» и фиксируется так в журнале (не вечный running); завершённые
  джобы читаются из журнала и после рестарта. Квоты `VELES_QUOTA_DOCS`/`_MB`
  (0 = без лимита, дефолты 1000 док / 2048 МБ) проверяются ДО очереди и ДО записи
  L0: документы - 403, суммарный размер L0 - 413. Аудит: событие `upload` в
  `ingest-audit.jsonl` (by, размер, document_id, job_id, sha256, исход, source=api).
  L0: `VELES_DATA/uploads/<user_id>/` (static - `owner`).
- **Ревизии** (`ingest_document`, K3 - без дублирования): тот же document_id с
  другим sha256 -> r{n+1} + архивация; тот же sha -> unchanged; API-джоб несёт
  action/revision_id («обновлён до r2»).
- **ACL** (`veles/policy/identity.py` + `retriever.py`): у аутентифицированного
  пользователя corporate-режима к группам добавляется личная `user:<uid>`, загруженный
  документ несёт только её; админ (VELES_ADMIN_EMAILS) дополнительно получает
  wildcard `*` - `hybrid_search` пропускает групповой фильтр (ревизионный остаётся).
  Static-режим не изменён (владелец, группы resolver; владелец - админ и может
  задать access_groups параметром; не-админу параметр - 403, инвариант 5).

## Обоснование реализации upsert (вариант «живой append + атомарный overlay»)

Запрещённый путь - полный rebuild (27 мин на 158k узлов). Рассматривались:

1. **Per-user overlay-индекс** (отдельный бандл на пользователя + merge в retrieval):
   потребовал бы нового merge-шва в `hybrid_search`/AnswerPolicy и второго хранилища
   индексов; rejection-критерии и RRF считались бы по-разному для двух бандлов.
   Отклонено как чужой код в горячем шве при равном итоге.
2. **Атомарный append+swap полного индекса** (переписывать весь бандл на диск после
   каждой загрузки): корректно, но O(весь индекс) записи на каждую загрузку
   (~243 МБ при 158k узлов) - операционно плохо при частых загрузках.
3. **Выбранное: гибрид** - новые узлы добавляются в живой бандл в памяти (поиск
   видит их мгновенно, рестарт не нужен), а дельта (мета новых узлов + патчи
   статусов старой ревизии + векторы + bm25-записи) накапливается в одном файле
   `INDEX_DIR/overlay.npz` с атомарной записью (tmp+replace, одним файлом - мета и
   векторы не расходятся). `load_index` применяет оверлей после снапшота: загрузки
   переживают рестарт без пересборки. Полная `build_index+save` стирает оверлей -
   снапшот снят с канона, куда загрузки уже легли (дубли исключены по построению).
   Стоимость апсерта: O(узлы документа) эмбеддингов + O(объём оверлея = только
   пользовательские загрузки) записи, индекс основного корпуса не переписывается.

Существующие node_version_id не меняются никогда: у старой ревизии патчится только
`status=superseded` в мете - тот же итог, что дал бы полный rebuild (K3: узлы архива
хранят свои id). Порядок мутаций живого бандла безопасен для поиска из других
потоков (воркер пишет, запросы читают без локов): мета - атомарные присваивания,
векторы - ids раньше матрицы (`NumpyFlatStore/FaissFlatStore.add` так уже устроены),
BM25 - ids последними в `add` (переставлен после doc_lens/tfs/df, поведение для
однопоточных вызовов не изменилось; между шагами читатель видит либо старое, либо
целое новое состояние, исключений чтения нет).

## Отступления от буквы брифа (зафиксировано)

- «access_groups документа = группы пользователя из identity» уточнено до
  **личной группы `user:<uid>`**: у JwtHeaderResolver все пользователи получают
  одинаковые VELES_IDENTITY_GROUPS, и «чужой документ невидим в поиске» при общих
  группах невыполним - документ, помеченный общими группами, виден всем. Личная
  группа делает требование истинным; админ может расширить видимость параметром
  access_groups (только админ). Per-user маппинг групп остаётся будущей фазой.
- Квота «число документов» считается по текущим L0-файлам пользователя
  (`uploads/<user>/`): перезапись существующего имени не увеличивает счётчик.
- app.py получил 9 добавленных строк вместо «одной строки include_router»:
  import, include_router, `app.state.veles = state` и два шва в state
  (identity_fn/pipeline_fn) - иначе роутеру нечем пользоваться той же личностью
  и тем же пайплайном (инвариант 6); строки только добавлены, конфликт с K6
  минимальный.

## Не проверено

- **PDF-загрузка end-to-end**: на стенд docling в venv есть, но настоящий PDF через
  API не прогонялся (E2E - текст; PDF покрыт unit-веткой «нет docling -> failed»).
  Docling-парс создаёт tempdir с картинками, который после save_document не
  удаляется (унаследовано от корпусного конвейера, вне скоупа K4).
- **Многопотная гонка чтение/запись индекса** под нагрузкой: корректность
  обеспечена порядком мутаций и проверена тестами на прерывистом доступе, но
  специализированного стресс-теста (параллельные query во время ingest) нет.
- **Рестарт с незавершённым джобом на живом фасаде**: семантика «failed при
  следующей проверке статуса» покрыта unit-тестом с двумя boot-id и журналом;
  kill реального uvicorn посреди джоба не выполнялся.
- **Масштаб оверлея**: рост overlay.npz на сотнях пользовательских загрузок не
  замерялся (переписывается целиком, O(сумма загрузок)); при больших объёмах -
  периодическая полная сборка, которая оверлей гасит.
- **Квоты при параллельных загрузках**: два одновременных POST могут оба пройти
  проверку до записи L0 (лёгкое превышение; очередь исполняет последовательно,
  но проверка квоты в роутере вне лока).
- **WebUI/загрузка из Open WebUI**: UI-загрузка вне скоупа брифа; проверен API.
