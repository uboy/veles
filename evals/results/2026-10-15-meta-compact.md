# Eval: сквозная валидация компактной RAM-меты (index-format, фаза 6 части 2), 2026-10-15

## Что доказывается

Фаза 6 части 2 плана `docs/plan/index-format/plan.md` (бриф
`docs/plan/briefs/2026-10-15-meta-compact.md`): реализация 756c7bf (ветка
feature/meta-compact, worktree veles-meta) - `CompactNodeMeta` в `load_index`
(texts - per-node zlib-чанки в одном блобе, интернирование повторяющихся строк,
K4-setitem поверх) при неизменном формате диска - держит эквивалент выдачи,
round-trip и >= 2x выигрыш RAM без деградации latency запроса.

## Метод

Скрипт `evals/meta-compact-validate.py` (создан этим же заходом; все проверки -
assertions, числовые гейты применяются после всех секций - один прогон печатает
замеры всех четырёх пунктов даже при упавшем гейте; успех = `VALIDATION-PASS`,
код 0):

1. (а) Синтетический индекс **2200 узлов / 44 документов** с русскими текстами
   (11 тем с ключевых словами в той же словоформе; junk-пустышки «Утратил
   силу.»/телефоны по 2 на документ; deleted/superseded-доки на уровне
   документа, как `build_index`; видео-узлы с таймкодами; rare-поля).
   Поисковые тексты - с префиксом пути заголовков, как indexer.py:108-110.
   Эталон - бандл с **dict-метой из тех же файлов на диске** (json.loads);
   валидируемая форма - **перезагрузка продовым путём** `load_index`
   (indexer.py:194). 66 запросов (>= 50 по заданию): темы, кодексы
   (legal_boost), тема в названии (title_boost), junk, граничные (пустой,
   несуществующий), kwargs-варианты revision/allowed_groups/filter_junk.
   Сверка - полная распаковка Evidence: (id, text, rrf, rrf_base, dense_rank,
   bm25_rank + все поля Citation) бит-в-бит; junk-набор - прямой обход обеих
   мет через `is_junk_node`; tombstone-узлы не в выдаче.
2. (б) `load_index` -> `bundle.save` -> meta.json по-ключевому равен исходному
   payload (тексты байт-в-байт, порядок ключей сохранён), рестарт
   перечитанного каталога снова компактен и бит-в-бит.
3. (в) Латентность `hybrid_search` на компактной мете vs dict-мете, пакет 30
   запросов, **лучшее из 5 прогонов**, прогрев перед замером; меряются ОБА
   режима - дефолт прода (`filter_junk=False`) и горячий путь брифа
   (`filter_junk=True`, материализация на каждого кандидата). Гейт < +5%.
4. (г) RAM: синтетика **100 000 узлов** с текстами ~1 КБ; каждый вариант
   (dict после json.loads / CompactNodeMeta) в **своём свежем подпроцессе**
   (`--child-ram`). Гейт-метрика - живые аллокации tracemalloc после gc
   (резидентная мета; контрольные тексты выборочно сверяются с ожидаемыми -
   форма обязана реально читать данные). RSS-прирост (psutil 7.2.2, база -
   сразу после импортов, итог - после gc) и пик аллокаций построения -
   информационные. Гейты: >= 2x ниже dict и <= 0.5 ГиБ.
5. VELES_DATA - tmp-каталог ОС, удаляется в конце; захардкоженных машинных
   путей нет; pytest-точка входа `test_meta_compact_validation` +
   регистрация в `evals/conftest.py` (прецедент index-format-validate.py).

Питон 3.11.9, numpy 2.4.6, Windows, системный python.

## Результаты (прогон 2, каноническая команда)

**(а) эквивалентность - PASS**: 66 запросов (непустых 66), evidence
(id, text, rrf, ранги, цитаты) бит-в-бит на всех; junk-набор совпал
(88 пустышек); tombstone не в выдаче; компактный блоб 1.1 МБ.

**(б) save round-trip - PASS**: meta.json после load -> save по-ключевому
равен исходному (2200 узлов, 24 640 полей, тексты байт-в-байт); рестарт
каталога снова компактен.

**(в) latency - FAIL**: dict 0.73 мс/запрос (0.022s пакет 30) vs компакт
**2.68 мс/запрос (0.081s)** = **+266.3%** на дефолте (filter_junk=False);
горячий путь (filter_junk=True): dict 0.85 мс vs компакт 2.98 мс =
**+250.1%**. Гейт плана < +5% не выполнен с запасом в разы; три прогона
подряд дают +266-291% (дефолт) и +246-254% (горячий путь) - воспроизводимо.

**(г) RAM - PASS (гейты)**: живые аллокации tracemalloc после gc:
dict **461.2 МБ** vs компакт **169.7 МБ** = **2.7x ниже** (гейт >= 2x),
компакт <= 0.5 ГиБ (гейт выполнен). Информационные: RSS-прирост +502.5 vs
+314.9 МБ (1.6x - шум освобождения промежуточных форм поверх базы, поэтому
гейт на tracemalloc); пик аллокаций построения dict 464.9 vs компакт
644.9 МБ (у компакта выше - распарсенный dict и компактная форма живут
одновременно); meta.json в JSON 299.7 МБ.

## Диагностика корня отказа (в) (пробы этого же захода, ад-хок)

- один `node_meta.get(nid)`: dict **0.07 мкс**, компакт **10.46 мкс** (~150x);
  authorized-паттерн (прочитать только status/access_groups) - 9.94 мкс:
  `hybrid_search` вызывает `node_meta.get` на КАЖДОГО кандидата
  (retriever.py:211 authorized - до 2x40 вызовов на канал; буст-циклы
  :269-275 и :290-302; survivor-скан :307-316; evidence :326) - ~150-250
  материализаций на запрос;
- структура стоимости: zlib-распаковка текстового чанка **8.18 мкс** из 13 мкс
  полного `__getitem__` (meta_compact.py:225-262, :341-353) - узел
  материализуется ЦЕЛИКОМ с текстом даже когда нужны 2 скалярных поля;
  копия per-node записи без sentinel-материализации - 0.78 мкс;
- помеха канала поиска исключена: замена memmap-матрицы компактного бандла на
  ndarray не меняет время (2.394 vs 2.393 мс/запрос); BM25 у обеих сторон из
  одного bm25.npz.

Бриф предусматривал этот риск («MutableMapping материализует dict узла на
каждый доступ... при худшем раскладе - кэш последних материалованных») -
кэш в реализации 756c7bf отсутствует. Возможные направления решения (не
исполнялись, решение за владельцем): кэш последних материализованных узлов;
быстрый путь без распаковки текста для доступа к скалярным полям (статус/
группы/название читаются из интернированных колонок); перенос junk/authorized-
фильтров на предвычисленные массивы. Абсолютные цифры на прода-корпусе 235 754
узлов будут другими (базовая стоимость каналов выше), но гейт плана -
относительный, и он не выполнен.

## Вердикт

**FAIL** - фаза 6 не подтверждена: критерий (в) плана «latency запроса < +5%
к dict-версии» не выполнен - деградация **+266.3%** на дефолтном пути и
**+250.1%** на горячем пути (2.68-2.98 мс против 0.73-0.85 мс на запрос,
пакет 30, лучшее из 5; воспроизводимо в 3 прогонах). Причина - материализация
узла целиком с zlib-распаковкой текста (~10 мкс) на каждый из ~150-250
`node_meta.get` в `hybrid_search`. Остальные критерии фазы выполнены:
(а) эквивалентность выдачи бит-в-бит на 66 запросах (+ junk-фильтр, tombstone),
(б) save round-trip по-ключевому равен, (г) RAM меты 461.2 -> 169.7 МБ
(2.7x, гейт >= 2x; компакт 169.7 МБ <= 0.5 ГиБ). Независимое ревью фазы не
проводилось - до него имеет смысл править горячий путь (варианты в
«Диагностике»), затем перегнать этот eval.
