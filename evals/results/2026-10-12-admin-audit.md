# Eval: сквозная валидация журнала аудита на живом uvicorn-сервере (admin-audit, фаза 3), 2026-10-12

## Что доказывается

Фаза 3 плана `docs/plan/admin-audit/plan.md` (бриф
`docs/plan/briefs/2026-10-12-admin-audit.md`): журнал аудита пишется во все
значимые действия, виден админу через GET /v1/admin/audit с фильтрами и
пагинацией, ротируется без потери событий, не вырождает латентность поиска и
не собирает секреты. Реализация - коммиты ca7685c + a008982 (ветка
feature/admin-audit): `veles/audit.py`, точки записи в `veles/api/app.py` и
`veles/api/documents.py`, вкладка «Аудит» в админке.

## Метод

Живой контур (не TestClient), каркас - как `evals/image-channel-e2e.py`:

1. Приложение - настоящий `create_app()` под **настоящим uvicorn 0.40.0**
   на 127.0.0.1 (свободный порт), клиент - реальные HTTP-запросы **httpx
   0.28.1** (python 3.11.9, Windows; `trust_env=False` - иначе системный
   http_proxy перехватывал петлю 127.0.0.1 и отдавал 502).
2. Identity-режим **jwt** с известным секретом (`VELES_IDENTITY_JWT_SECRET`);
   токены админа (`admin@corp.ru` из VELES_ADMIN_EMAILS) и пользователя
   (`ivanov@corp.ru`) минтятся `veles.policy.identity.sign_hs256`, ходят
   заголовком X-OpenWebUI-User-Jwt.
3. LDAP-вход - настоящий POST /v1/auth/ldap против in-process каталога
   ldaptor/Twisted (пользователь petrov, bind ldap3 по DN-шаблону), как в
   `evals/ldap-identity-validate.py`.
4. Индекс/эмбеддер - детерминированный hashing (канон репо: evals без
   загрузки моделей), llm=None; настоящий пустой индекс в tmp - чтобы upload
   доходил до done и regroup/delete работали по канону. Предмет валидации -
   слой аудита, не модель.
5. VELES_DATA - tmp-каталог ОС (журнал, канон, индекс, groups.json),
   удаляется в конце; VELES_AUDIT_ROTATE_MB=1 (сценарий г); лимит запросов
   выключен (VELES_RATE_LIMIT_RPM=0 - не предмет валидации). Пути - от
   `__file__`, скрипт работает из любого cwd.

## Команда

```
cd C:/Users/devl/proj/veles-admin-audit && python evals/audit-validate.py
```

Скрипт `evals/audit-validate.py` создан этим же заходом. Успех - финальная
строка `VALIDATION-PASS`, код возврата 0; любая ошибка - `VALIDATION-FAIL`
и код 1. Итерации до зелёного прогона (обе - дефекты СКРИПТА/среды, не
реализации): (1) healthz отдавал 502 - httpx шёл через системный прокси,
исправлено `trust_env=False`; (2) VALIDATION-FAIL на фильтре q - скрипт
ожидал 3 совпадения, журнал корректно вернул 5 («закупок» сидит ещё и в
target document_regroup/document_delete - там target=document_id);
ожидание переписано вычисляемым из файла журнала независимым фильтром.

## Наблюдения (не блокируют)

1. После ротации GET /v1/admin/audit читает **только текущий файл**
   (total=1 сразу после сдвига) - ротированная история остаётся на диске
   (audit.jsonl.1) и в API-выборку не подмешивается. Это соответствует
   реализации чтения (`AuditLog.read` открывает `self.path`); для владельца
   «что было до ротации» - чтением файлов. Если понадобится единая выборка
   через API - отдельная задача, сейчас поведения плана не нарушает.
2. ts событий имеет точность до секунды (timespec="seconds") - при
   нескольких действиях в одну секунду порядок внутри секунды читается по
   порядку строк файла (append-only), фильтры since/until на границах
   ведут себя предсказуемо (граница включительная, проверено).
