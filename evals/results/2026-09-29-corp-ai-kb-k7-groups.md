## Что сделано

- **Реестр групп** (`veles/policy/groups.py`): id (ascii-слаг
  `[a-z0-9][a-z0-9_-]*`), человекочитаемое название, состав (identity, lower/strip).
  Дефолтные три (решение владельца 29.09): `all` «Видно всем», `on-request`
  «Видно по запросу», `test-dept` «Тестовый отдел». `all` - неявно все
  аутентифицированные (в конфиге members не задаётся). Файл-шаблон с дефолтами
  создаётся лениво (первый `GET /v1/groups`); чтение конфига - на каждый вызов
  (как `uploads_root`/`admin_emails`), правка состава админом - без рестарта фасада.
- **Identity** (`veles/policy/identity.py`): `all` в groups каждого
  аутентифицированного + membership не-all групп из конфига
  (`membership_of(uid)`); админ (VELES_ADMIN_EMAILS) дополнительно wildcard `*`
  (K4). Static/bearer-владелец получает все определённые группы
  (`allowed_groups`), но НЕ произвольные access_groups вне конфига - семантика
  K4 («нет права - не видно») сохранена.
- **Загрузка** (`veles/api/documents.py`): `group=<id>` (multipart-поле или JSON)
  доступен каждому аутентифицированному; невалидная группа - `400` с перечнем
  доступных, проверка ДО квоты и записи L0. Без `group` - личная `user:<uid>`
  (дефолт K4 сохранён). `access_groups` от клиента - по-прежнему только админу
  (инвариант 5). K3-ревизии: группа берётся из НОВОЙ загрузки (job.groups ->
  doc.access_groups, ветка не менялась - покрыто тестом).
- **GET /v1/groups** (`veles/api/groups.py`): id + название, служебные `user:*`
  не показываются, состав (members) не раскрывается; авторизация - та же
  личность, что у остальных API (шов `app.state.veles`).
- **app.py** - ровно 2 добавленные строки (import + `include_router`), как K4
  (файл правит параллельная K8, правки сведены к минимуму).
- Поиск/чтение не менялись: ACL-фильтр по access_groups работает с K3/K4,
  документ с group=<id> отфильтровывается существующим `hybrid_search`/
  `_visible_by_groups`.

## Обоснование хранения групп: файл <VELES_DATA>/groups.json, а не env JSON

Бриф оставлял выбор (env JSON `VELES_GROUPS` против файла в VELES_DATA). Выбран
**файл** (`<VELES_DATA>/groups.json`, путь переопределяется `VELES_GROUPS_FILE`):

1. **Кто и как правит.** Состав групп - многострочный список email'ов, который
   админ правит руками. Env JSON обязан быть одной строкой без пробелов - легко
   сломать, тяжело читать; docker `env_file` не снимает кавычки (значение
   берётся литерально) и не переносит многострочные значения, т.е. JSON в .env
   кита пришёл бы в контейнер с литеральными кавычками.
2. **Разделение секретов и данных.** `.env` кита хранит сгенерированные секреты
   (chmod 600): частые правки состава групп рядом с ними - лишний риск задеть
   секрет. `<VELES_DATA>` - bind-каталог данных кита, он и так редактируется
   админом (канон, индекс).
3. **Единообразие паттернов чтения.** Env в veles читается на вызов
   (`uploads_root`, `admin_emails`) - файл групп читается так же на каждый
   вызов: правка состава действует без рестарта фасада (env-правка в docker
   всё равно требовала бы пересоздания контейнера).
4. **Fail-closed.** Файла нет - дефолтные три группы; файл битый - НЕ
   перезаписывается (правка админа не затирается), действуют дефолты:
   membership пуст, не-all документы только сужают видимость, расширения нет.
   Тест `test_corrupt_groups_file_fail_closed` фиксирует оба свойства.
5. **Где живёт название.** В конфиге рядом с id (человекочитаемое - данные
   группы, а не кода); `GET /v1/groups` отдаёт пары id/title для будущего UI.

Материализация шаблона - ленивая (первый `GET /v1/groups`), а не при старте
фасада: см. «Отступления».

## Отступления от буквы брифа (зафиксировано)

- «Дефолтные три создаются автоматически при старте фасада»: группы **действуют**
  всегда (дефолт в коде), но файл-шаблон материализуется лениво - первым
  `GET /v1/groups`, а не при старте. Причина: единственная точка записи конфига -
  новый роутер, app.py не трогался сверх include (ограничение параллельной K8),
  а запись при старте/импорте модуля плодила бы файлы в repo data из тестов.
  Операционно для админа разницы нет: до первого GET /v1/groups дефолтные группы
  и так работают, после - видно, где править состав.
- `_document_groups` (static-дефолт) теперь вычитает из групп владельца
  производные группы чтения (all + определённые в конфиге): иначе каждая личная
  загрузка static-владельца молча становилась бы «видно всем». Загрузка с
  явным VELES_ALLOWED_GROUPS=<определённая группа> даёт дефолт personal -
  edge-case, задокументирован здесь.
- Тест `test_acl.py::test_static_resolver_from_env`: точное равенство
  `allowed_groups` заменено на проверку надмножества - контракт изменён самой
  фазой (all неявен, определённые группы у владельца).

## Не проверено

- **UI выбора группы в Open WebUI** - вне скоупа фазы (бриф, «чего НЕ делаем»);
  проверен API (`group=` в multipart/JSON, `GET /v1/groups`).
- **Подмешивание групп Open WebUI** кастомными заголовками
  (`{{USER_GROUP_IDS}}`) - факт «не передаются штатно» проверен по исходникам
  v0.11.4, но живая связка с настроенными кастомными заголовками не
  воспроизводилась.
- **Масштаб**: чтение groups.json на каждый запрос/резолв identity не
  замерялось под нагрузкой (файл на сотни членов - единицы КБ, чтение с
  page-cache; rate-limit K6 ограничивает частоту).
- **Гонка правки конфига на лету**: админ правит файл в момент запроса -
  чтение атомарностью не защищено (частичная запись даст fail-closed дефолт на
  один запрос; запись шаблона атомарна tmp+replace, ручные правки админа -
  на его совести, как и правка .env).
- **Миграция существующих документов** в группы - вне скоупа (бриф); старые
  загрузки остаются при user:<uid>/personal, перегрузка с group= создаёт новую
  ревизию с новой группой (покрыто тестом).
- **Админ-API групп** - вне скоупа (состав правится файлом).
