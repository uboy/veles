# Eval: сквозная валидация бинарного формата индекса (index-format, фаза 3), 2026-10-14

## Что доказывается

Фаза 3 плана `docs/plan/index-format/plan.md` (бриф
`docs/plan/briefs/2026-10-14-index-binary-format.md`): реализация 62873e1
(ветка feature/binary-index, worktree veles-bidx) - bm25 в CSR на чистом numpy
вместо tfs-словарей, формат bm25.npz с чтением старого bm25.json, mmap базовой
матрицы в load_index - НЕ меняет результаты поиска (бит-в-бит со старой
реализацией) и даёт выигрыш по памяти и времени загрузки на масштабе.

## Метод

Скрипт `evals/index-format-validate.py` (создан этим же заходом, все проверки -
assertions, финальная строка `VALIDATION-PASS`, код 0):

1. Эталон - **точная копия `Bm25Index.search` из v1** (git 0b44e9d, до CSR):
   питоновский цикл по `tfs` (list[dict])/`df` (dict), тот же `math.log`,
   арифметика float64, стабильная сортировка. Питон 3.11.9, numpy 2.4.6,
   Windows, системный python.
2. Корпуса - детерминированная синтетика (seed фиксируется): термин-везде +
   убывающие веса словаря + повторы термина внутри документа + разброс длин;
   запросы - 1-5 терминов с повторами, термин-везде, несуществующие, пустой.
3. Замеры (в)/(г) - **в двух свежих подпроцессах** того же скрипта
   (`--child-load`): tracemalloc вокруг загрузки + psutil (7.2.2) пиковый RSS
   (peak_wset); скорость - лучшее из 3 загрузок без трассировки. Прогрев кэша
   ОС - одинаковая процедура у обоих форматов. Оба формата собраны из ОДНОГО
   payload: генератор пишет старый bm25.json, новый bm25.npz получается
   легаси-загрузкой + save (заодно легаси-путь проверен на 100к).
4. mmap (д) - через настоящий `load_index` (meta.json + bm25.npz +
   numpy_matrix.npy + numpy_ids.json во временной папке), эталон - тот же файл
   обычным `np.load`; add() после mmap и рестарт на пересохранённом каталоге.
5. VELES_DATA - tmp-каталог ОС, удаляется в конце (проверено: каталог
   отсутствует после прогона); захардкоженных машинных путей нет.

## Результаты

Синтетический набор (в)/(г): **100 000 узлов, nnz 6 603 385, avgdl 72.0,
601 термин**; bm25.json **140.6 МБ** -> bm25.npz **12.0 МБ** (11.7x меньше
файл).

**(а) бит-в-бит**: корпус 2200 доков (nnz 120120), 325 запросов, top-10
`(id, score)` - точное равенство с эталонным циклом v1 (те же пары в том же
порядке, скоры бит-в-бит); непустых выдач 323 (пустой запрос и
несуществующие термины дают [] в обеих реализациях). Дополнительно
не-дефолтные k1=1.2/b=0.3: 300 доков x 40 запросов - тоже точны.

**(б) round-trip старого формата**: payload v1 (tfs/df-словари, 500 доков)
-> load старого bm25.json -> 85 запросов == эталон; save на месте пишет
bm25.npz и оставляет рядом СИНХРОННЫЙ bm25.json (payload v1) - каталог читается
старым кодом без пересборки (ревью раунд 1, находка 2: удаление json делало
каталог односторонним); повторный load - 85 запросов == эталон, поиск по
синхронному json == поиск по исходному payload.

**(в) память** (критерий (б) плана - «RSS при загрузке >= 3x»; прогон 15.10.2026
после ревью раунда 1, подпроцессы):
- гейт - **прирост пикового RSS процесса при загрузке**: старый **+398.2 МБ**,
  новый **+85.9 МБ** - **4.6x** ниже, порог >= 3x выполнен;
- полный пик RSS подпроцессов (инфо, не гейт): старый **527.6 МБ**, новый
  **212.3 МБ** (2.5x; в RSS входит одинаковая база интерпретатора+numpy
  ~100-130 МБ, размывающая отношение на 100к узлах - см. «Расхождения плана
  и реальности» plan.md);
- пик аллокаций tracemalloc (инфо, не гейт): старый **562.3 МБ**, новый
  **84.5 МБ** (6.7x). Ревью раунд 1: первый вариант гейта именно на этой
  метрике был подменой критерия плана (RSS) - переведена в информационные,
  гейт переведён на RSS-прирост;
- контроль на том же наборе: поиск старого и нового формата идентичен
  бит-в-бит на 100к узлах (top-10 совпал целиком).

**(г) скорость загрузки** (лучшее из 3, тот же набор): старый **3.29s**,
новый **0.23s** - **14.2x быстрее**.

**(д) mmap**: `load_index` отдаёт `np.memmap` (400 строк); 25 векторных
запросов (top-8) и 5 bm25-запросов - попарно идентичны поиску по обычному
ndarray; `add()` после mmap работает (402 строки, новые доки ищутся, выдача
== эталону с тем же add); save пишет полную матрицу (402, 384), рестарт на
пересохранённом каталоге находит добавленные доки, матрица снова mmap.

## Повторный прогон через pytest и фикс (тем же днём)

матчит дефолтный `python_files` - pytest собирал 0 тестов. Починено без

1. В скрипт добавлена тестовая точка входа `test_index_format_validation()`

   падение теста. Заодно temp-каталог стал ленивым (не создаётся на импорте
   модуля - `pytest --collect-only` не оставляет мусора), ретраи очистки

2. Добавлен `evals/conftest.py` с `pytest_collect_file`-хуку, собирающим

## Ревью раунд 1: правки и повторный прогон (15.10.2026)

Независимое ревью нашло две проблемы, обе исправлены этим же заходом:

1. **Подмена метрики критерия (б)**: критерий плана - «RSS при загрузке
   >= 3x ниже», фактический RSS давал 2.5x, а PASS брался с пик-аллокаций
   tracemalloc (6.7x); раздел plan.md «Расхождения» пустовал. Исправлено:
   гейт переведён на прирост пикового RSS при загрузке (сэмплы RSS в
   фоновом потоке подпроцесса, отдельная загрузка без tracemalloc) -
   **4.6x, порог 3x выполнен**; tracemalloc и полный пик RSS оставлены
   информационными метриками; расхождение (почему полный пик 2.5x - база
   интерпретатора+numpy) зафиксировано в plan.md. Регрессия -
   tests/test_eval_memory_gate.py (AST: гейт 3x обязан быть на RSS,
   tracemalloc гейтом быть не может, отсутствие RSS = FAIL, не PASS).
2. **Односторонний каталог**: save() удалял bm25.json - после записи откат
   кода на v1 падал FileNotFoundError, восстановление только пересборкой
   старым кодом. Исправлено: save() пишет bm25.npz И синхронный bm25.json
   (payload v1, tfs/df собираются из CSR только на время сохранения);
   v1-читаемость проверяется в eval (синхронный json == исходный payload,
   поиск бит-в-бит) и тестом tests/test_bm25_binary.py::
   test_save_keeps_legacy_json_v1_readable.

Повторный прогон канонической командой после правок: `python
