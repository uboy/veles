### Находки

- **P1-1. Владельческий токен в ссылках цитат в static-режиме.** `veles/api/app.py`:
  `signed = bool(link_secret)` (строки 222-239, вызов в static идёт с `link_secret=""`) →
  подписанные ссылки в static не строятся, и функция K19
  (`integrations/openwebui/functions/veles_knowledge.py:197-211`) рендерит fallback-ссылки с
  `token=<владельческий токен>`. Любой пользователь WebUI стенд получает в ответе рабочий
  владельческий bearer: DELETE документов, чтение трекера, act-as-загрузки. Фиксы-кандидаты:
  минтить подписанные ссылки при заданном VELES_LINK_SECRET независимо от режима (и задать секрет
  на стенд); либо перевести стенд в identity-режим; либо в K19 не отдавать token-ссылки. Оценка M.
- **P1-2. «Личное хранилище» K19 в static не приватно.** act-as-документ получает группы
  `[user:<email>, personal]`, но запрос функции идёт владельческим токеном → `_owner_identity()`
  (`app.py:399-401`, admin=True, все группы) → «личные» документы находимы любым пользователем.
  DEPLOY-стенд.md и докстринг обещают «личное». Фикс: предупреждение в доках + решение по режиму стенд
  (совпадает с P0-1 части 2). Оценка S (доки) / M (перевод режима).
- P2-1. Гонка очереди с читателями: воркер (`veles/ingest/queue.py:627`) мутирует node_meta/ids/bm25
  живого бандла без лока, `knowledge_stats`/`_resolve_revision` итерируют ту же мету
  (`app.py:690,140`) → редкий `RuntimeError: dictionary changed size during iteration` → 500.
  Фикс: RLock вокруг апсерта/томбстоуна и итераций меты. Оценка M.
- P2-2. `link_secret = ... or token` (`app.py:348`): при незаданном VELES_LINK_SECRET в
  identity-режиме ключом HMAC становится владельческий bearer — раскрывается только дайджестом, но
  смешение ключевого материала с bearer рискованно при будущих рефакторингах. Задокументировать.
  Оценка S.
- P2-3. Кит: слой `pip install ".[st,faiss]"` стоит после `COPY veles`
  (`deploy/kit/Dockerfile:19-21`) — правка кода инвалидирует слой и перекачивает сотни МБ;
  комментарий про deps-кэш преувеличен (спасён только torch). Фикс: st/faiss в deps-слой. Оценка S.
- P2-4. Разделитель VELES_DATA: `source_view` парсит `split(":")` (`app.py:562`), остальные —
  `os.pathsep` → на Windows-деве ломается, на проде незаметно. Фикс: `os.pathsep` везде. Оценка S.
- P2-5. Таймаут LLM жёстко 60 с (`veles/api/llm.py:37`, `timeout_s: float = 60.0`), env не
  настраивается; при деградации V100 каждый вопрос ждёт 60 с до extractive-фолбэка. Фикс:
  `VELES_LLM_TIMEOUT`. Оценка S.
- P2-6. Внутренняя топология (<internal-domain>-хостнеймы и пр.) в docs/evals — разрешено брифом владельца,
  кит это вырезает (content-скан ловит sk-ключи и часть IP, но не <internal-domain>-имена). Пометка: если репо
  станет публичным — вычистить. Решение владельца. Оценка S.
- Провенанс K17: первичный лог стенд-бенча был утрачен при чистке 01.10 (перенесён в каталог и
  удалён вместе с ним; в репо не попал из-за глобального gitignore `*.log`). Восстановлено
  перегонкой той же командой на том же прод-индексе — см. «Дополнение 01.10» в
  `2026-09-30-k17-reranker.md` и артефакт `k17-artifacts/k17-bench-rerun-20261001.log`.
- Замечена неактуальность деплоя стенд: его `veles/retrieval/reranker.py` отличается от main тремя
  строками докстринга (скоринг-путь байт-в-байт совпадает; сверка md5 по всем 33 py-файлам
  `veles/`); синхронизируется следующим деплоем, срочно ничего не требует (реранкер выключен).

### P0. Изоляция поиска для обычного пользователя WebUI отсутствует

`veles_knowledge.pipe()` шлёт `/v1/knowledge/query` владельческим токеном из valves → фасад
резолвит `_owner_identity()` (admin=True, все группы) → вопрос ЛЮБОГО пользователя ищет по ВСЕЙ
базе, включая чужие личные документы, и возвращает рабочую ссылку на чужой документ. Зафиксировано
в eval K19 §4 как ограничение («act-as для query фасад не поддерживает»); ревью классифицирует как
P0 для многопользовательского пилота. Прямой API с пользовательским JWT изолирован корректно
(leakage 0%, живой E2E 29.09) — разрыв именно в связке WebUI-функция → query. Следствие: сценарий
«сотрудник спрашивает про закрытый документ» сегодня даёт ответ, а не abstain. Чинится только
вместе с продуктовым решением: какие группы обычный пользователь видит по умолчанию. Живая
демонстрация на двух пользователях не проводилась — находка по коду, оба агента сошлись независимо.

### Приоритеты покрытия (с оценками трудоёмкости)

1. **[P0]** Изоляция query (выше) — требует решения владельца о группах по умолчанию (вариант:
   act-as/JWT для query + personal + явный список общих групп). Проверка: пользователи A/B на
   сервер; личный файл A с уникальным фактом; вопрос B через WebUI — сейчас получит цитату, тем же
   вопросом напрямую с JWT B — 0 чанков.
2. **[P1]** Ловушка «новый пользователь видит пустую базу» — включить демо-узлы в группу,
   видимую новым пользователям (час). Проверка: свежий пользователь, вопросы из demo-набора.
3. **[P1]** Приписка человеку при недоступности LLM: сейчас extractive-сырец без предупреждения
   (`llm_error` только в diagnostics); плюс замерить и зафиксировать время загрузки индекса 517 МБ
   при рестарте фасада (час).
4. **[P1]** Удаление на глазах у заказчика: выдача чистится только рестартом (известный P2,
   подтверждён живым циклом 01.10); в DEPLOY-стенд/kit README всё ещё «сразу». Фикс: правка доков +
   честный warning в ответе DELETE либо reload по пути query (1-2 ч).
5. **[P1]** «Не по базе» на демо-корпусе: 3-5 посторонних вопросов (борщ / погода / чужой домен) →
   ожидаем честный отказ; на мини-демо abstain не достигался (полчаса).
6. **[P1]** «Не советует утратившую силу как действующую»: 3-5 вопросов вида «действует ли …» на
   обоих контурах; проверен только CLI-кейс и один тип вопроса в проде.
7. **[P1]** Onboarding 10 пользователей одним чек-листом (админ создал → вошёл → спросил →
   загрузил) + бэкап-крон на сервер по образцу стенд (часы).
8. **[P2]** Группы при загрузке из чата (сейчас команда «загрузи для отдела» молча уйдёт в
   личную); DOCX/XLSX со структурой; аудит запросов и открытий ссылок.
