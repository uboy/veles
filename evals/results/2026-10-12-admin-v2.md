# Eval: сквозная валидация админ-панели v2 (admin-ui, спека v2), 2026-10-12

## Что доказывается

Админка v2 работает сквозным сценарием владельца на живом приложении
(раздел «Проверки» -> «Валидация» docs/plan/admin-ui/v2-spec.md):
массовая смена группы переводит и канон, и выдачу поиска (новая группа
находит, старая теряет), массовое удаление оставляет поиск пустым,
файловая задача с битым файлом честно падает и не оставляет L0-сироту,
а перезапуск -> отмена -> удаление из журнала проходят по контракту
задач v2; дубликат-детекция помечает вторую активную задачу с тем же
файлом. Реализация - коммит 29e0e51 (ветка feature/admin-ui-v2):
POST /v1/documents/{id}/groups, cancel/retry/delete джобов,
exists_in_base + duplicate_of в GET /v1/documents/jobs.

## Метод

Живой контур, без внешних сервисов (каркас - как у
evals/ldap-identity-validate.py):

1. Приложение - настоящий create_app() под TestClient (fastapi 0.141.1,
   httpx 0.28.1, python 3.11.9, Windows). Эмбеддер - детерминированный
   hashing (как в tests/test_delete.py), dim = EMBED_DIM: модели не
   загружаются, от сети валидация не зависит; фильтр по группам и
   очередь от эмбеддера не зависят.
2. Окружение - tmp-каталог ОС (VELES_DATA до импортов veles: канон,
   индекс, uploads, groups.json), удаляется в конце; изоляция разбора
   выключена (VELES_QUEUE_PARSE_TIMEOUT_S=0, как tests/conftest.py -
   spawn-потомок не наследует подмену окружения).
3. Конфиг групп - ДВЕ серверные группы: legal (петров) и fin (иванов);
   identity-профиль как ACL-тесты K4 (headers-режим, boss@corp.ru -
   админ, bearer-владелец). Плюс засеянный документ в каноне/индексе,
   не затронутый сценарием.
4. Документы - через настоящий цикл POST /v1/documents -> очередь ->
   парсер -> канон -> индекс (живой апсерт + overlay). Битый файл
   разбирается НАСТОЯЩИМ docling-адаптером (мусорные байты под .pdf).
5. Поиск - POST /v1/knowledge/query без LLM, оглавление -
   GET /v1/knowledge/stats; все проверки - assertions, каждая с
   человекочитаемым заголовком и деталями ответа.

## Результаты

Прогон 12.10.2026: **61 проверка пройдена, VALIDATION-PASS, exit 0**.

Акт 1 - массовая смена группы (2 документа иванова, личные user:ivanov@):
- инвариант 5: смена группы не-админом (петров, иванов) - 403, аноним - 401;
  пустой список/неизвестная группа - 400, чужой документ - 404;
- regroup обоих документов на legal: 200, nodes>=1, overlay_saved=true;
  манифест канона переписан (первичный артефакт, access_groups=['legal']);
- /v1/knowledge/stats (админ): оба документа groups=['legal'], старая
  личная группа потеряна;
- поиск: петров (legal) находит оба маркера («350 тысяч», «авансовый
  отчёт»), иванов (старая группа) - ни одного.

Акт 2 - массовое удаление выбранных:
- DELETE обоих - 200 (канон в trash, узлы выведены из поиска);
- поиск пуст у всех трёх лиц (петров, иванов, админ) по обоим запросам;
- в оглавлении только незатронутый засеянный документ.

Акт 3 - файловая задача с битым файлом (настоящий docling):
- multipart «битый.pdf» (мусорные байты) -> failed «не удалось разобрать
  документ (битый.pdf): Conversion failed ... docling-parse could not
  load document»;
- L0 удалён (битый файл не ест квоту), retry - 409 «L0-файл задачи не
  сохранился - повторите загрузку документа» (честный контракт провала
  разбора).

Акт 4 - перезапуск -> отмена -> удаление из журнала (провал с
сохранённым L0: пайплайн недоступен) + дубликаты:
- дубликат-детекция: на двух активных задачах с тем же файлом
  duplicate_of ровно у одной и ссылается на другую задачу пары;
  exists_in_base у обеих False;
- активную (queued/running) удалить нельзя - 409 «сначала отмените»;
- отмена queued и отмена running (воркер выведен из заблокированного
  пайплайна) - failed «задача отменена владельцем»; L0 отменённой
  сохранён;
- retry упавшей - 202, НОВАЯ задача с retried_from (проверено до двух
  степеней), retry активной - 409 «только упавшей»; cancel завершённой
  запись не меняет;
- delete завершённой из журнала - 200, дальше GET/DELETE - 404, в списке
  задач записи нет; неизвестная задача - 404 на всех трёх операциях.

## Ограничения

- Веб-интерфейс (admin.js/admin_page.html) сквозным браузерным прогоном
  не проверялся: скрипт валидирует API-контур владельца (тот же, что
  дергает UI); логика панели покрыта tests/test_admin_ui.py.
- Эмбеддер - hashing-стаб: валидируется ACL/очередь/журнал, не качество
  ранжирования.
- Отмена running проверена на заблокированном пайплайне (управляемое
  событие), а не на снятии живого дочернего процесса разбора - путь
  proc.kill() покрыт тестами test_audit_fixes/queue, в этом прогоне не
  воспроизводился.

## Вывод

Сквозной сценарий владельца из v2-spec («Проверки» -> «Валидация»)

и к поиску; управление задачами (retry/cancel/delete) и
дубликат-детекция работают по контракту; битый файл не оставляет сирот.
